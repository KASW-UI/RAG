## 阅读顺序

1. **想快速判断「这个项目能不能写进简历」** ⇒ 交付物 2（§六 给结论 ＋ §七 给收口清单）
2. **想知道「它到底是什么、有什么」** ⇒ 交付物 1
3. **想看「技术深度是真的吗」** ⇒ 交付物 3（三个机制 × 九项闭环，**每条都写了边界与不足**）
4. **想按十二维度核** ⇒ 交付物 4（**按阶段一等级评** ⇒ 维度 11 判「阶段一不适用」并给 P2 依据）
5. **想知道「还有什么没对齐」** ⇒ 交付物 5（**每条 11 字段** ⇒ 含 Go 出处 / 影响 / 是否阻断 / 阶段二恢复方案与通过标准）
6. **想看「这一轮到底做了什么」** ⇒ 交付物 6（逐任务：修改 / 命令 / 断言 / 实际结果）

## ⚠️ 三条最容易读错的口径

| 坑 | 正确读法 |
|---|---|
| **「十二维度」≠ judge 的「12 条跨组件不变量」** | 前者是 `twoStage.md` §七 的**工程审查维度**；后者是 judge §五 的**跨组件约束** ⇒ 两张表**不是一回事** |
| **交付物 4 必须按 §2.1（阶段一）评，不能按 §2.2（阶段二）** | 否则会把「生产级 SLO / 真实流量容量规划 / 灾备演练 / 灰度发布」算成「阶段一未过」⇒ **那正是 T-0.1 那个坑在交付物层的翻版** |
| **交付物 5 的「阻断 = 0」≠「没有差异」** | 意思是**每条差异都已定性**（已修 / 已签字 / C 类暂缓 / D 类不实现）⇒ **真破坏的两条（密钥链、共享层 R2）在 A 类实修里，不在清单里暂缓** |
