## 41. 跨组件组合行为验证：从局部语义到整体业务行为

### 41.1 验证目标

本阶段的目标不是重复验证单个组件，也不是把多个组件的功能说明拼接成一份报告，而是确认：

**当多个组件按照项目实际定义的调用关系共同完成一项操作时，它们之间的交互是否正确；Go
与 Spring Boot
的实现是否保持了所需的业务语义；局部行为组合后是否产生了新的问题。**

单组件验证与组合验证解决的是不同层次的问题。

单组件验证关注一个局部执行单元自身的输入、处理过程、输出和副作用。组合验证则关注多个执行单元之间的依赖关系，以及这些依赖关系如何共同影响最终结果。

一个组件单独运行正常，不代表它与其他组件组合后仍然正常。例如，两个组件各自都正确处理了自己的输入和返回值，但调用方可能错误理解了被调用方的返回结果；两个操作分别成功，但执行顺序可能导致中间状态不满足业务要求；每个局部错误处理都看似合理，但错误经过多层包装后，最终可能被错误地转换成成功结果。

以上仅用于说明组合验证的必要性。实际验证必须从当前项目的源码、配置、接口契约和业务行为中发现具体问题，不得预先假定项目一定存在上述情况。

本阶段必须分别回答以下问题：

1.  **局部行为是否已经得到确认？** 哪些已有结论可以直接复用，哪些结论仍然缺乏证据？

2.  **交互关系是否正确？** 各执行单元之间传递的数据、调用条件、返回结果和状态依赖是否符合实际契约？

3.  **组合后的行为是否正确？** 多个局部操作共同执行时，控制流、状态变化、错误传播和外部可观察结果是否符合预期？

4.  **Go 与 Spring Boot
    的组合语义是否一致？** 两种实现的差异是否改变了实际业务行为？

5.  **业务行为本身是否可以接受？** 即使 Go 与 Spring Boot
    的行为一致，是否仍然违反了明确的业务要求或系统不变量？

6.  **结论是否有足够证据？** 哪些问题已经得到确认，哪些只是推断，哪些必须继续调查？

不得使用单一的"通过"结论代替以上不同层次的判断。

### 41.2 验证对象必须从项目实际情况中发现

本阶段不预先规定必须分析哪些组件、接口、基础设施或业务场景。

Agent
必须先识别当前项目中实际存在的执行单元、交互关系和业务边界，再决定组合验证的范围。

#### 41.2.1 识别实际存在的执行单元

从当前项目的真实代码与运行结构中，识别可能参与同一业务行为的执行单元。

执行单元可以是任何具有实际职责、执行边界或交互关系的部分，例如一个函数、一个类、一段业务流程、一个服务、一个外部调用、一个数据访问操作，或由框架实际参与执行的机制。

以上只是可能的识别对象，不构成强制目录。不得为了匹配某种预设架构而将代码强行划分为指定类型。

对每个候选执行单元，先确认：

-   它实际负责什么行为。

-   它从哪里接收输入。

-   它依赖什么数据、状态、配置或其他执行单元。

-   它会调用哪些其他执行单元。

-   它会产生什么返回结果或副作用。

-   它的执行结果会影响哪些后续行为。

-   它的边界由显式代码、框架机制还是外部契约决定。

-   Go 与 Spring Boot 中对应的职责分别由什么实现承担。

不得仅根据目录名、包名、类名、函数名或注释认定职责。必须继续追踪实际实现，直到能够解释其执行行为。

如果 Java 使用框架机制承担了 Go
中显式实现的职责，应识别框架实际承担的部分；如果 Go 与 Spring Boot
的代码组织方式不同，应按照实际职责与行为建立对应关系，不要求代码结构一一对应。

#### 41.2.2 从真实交互关系确定组合边界

识别执行单元后，继续追踪它们之间真实存在的交互关系。

交互关系不仅包括直接函数调用，还包括其他能够影响执行结果的依赖。例如，某个执行单元读取另一个执行单元写入的数据；某个操作的执行条件取决于另一项操作的返回值；多个操作依赖同一份可变状态；某项框架机制改变了实际执行顺序或错误处理方式。

只有在代码、配置、协议或运行证据支持时，才能认定某种交互关系存在。

对于每条实际交互关系，记录：

-   交互双方分别是什么。

-   交互通过什么机制发生。

-   交互在什么条件下发生。

-   传递了什么数据、状态或控制信息。

-   接收方如何解释这些信息。

-   交互结果会影响哪些后续操作。

-   交互是否产生副作用。

-   交互失败或结果异常时，控制流如何变化。

-   Go 与 Spring Boot 是否采用不同的实现方式。

-   这种实现差异是否可能改变业务语义。

不得因为两个组件位于同一个业务域，就假设它们必然存在需要验证的直接交互；也不得因为两个组件不在同一个目录或服务中，就忽略它们通过数据、配置、事件或其他机制形成的实际依赖。

#### 41.2.3 从业务行为确定验证边界

组件组合的范围不能仅由代码结构决定。

Agent
必须从实际入口、业务操作和最终可观察结果出发，确认当前操作的起点与终点。

起点是该行为实际开始接受输入、触发执行或接收任务的位置；终点是该行为产生的业务结果、系统状态变化或外部可观察效果得到确定的位置。

在两者之间，识别所有对结果具有实质影响的执行步骤与依赖关系。

如果一个局部流程的结果会被其他流程继续使用，而这个后续使用可能改变当前验证结论，则必须根据实际依赖关系扩展验证范围。

如果某个执行单元与当前业务行为不存在实际依赖，也不会影响当前行为的正确性，则不应仅因为它存在于同一项目中就将其纳入验证。

**组合验证的边界由实际行为依赖决定，而不是由固定的组件数量、目录结构或预先指定的技术栈决定。**

### 41.3 复用已有结论，但不得扩大已有结论的适用范围

本阶段应当复用已经完成的单组件分析，避免无意义地重复工作。

但复用必须建立在明确的适用范围上。

#### 41.3.1 提取已有分析中的有效信息

从已有分析中提取与当前交互关系有关的内容：

-   已确认的局部行为。

-   输入条件与前置约束。

-   关键分支及其触发条件。

-   返回值及其业务含义。

-   状态读取与修改。

-   错误处理及其传播方式。

-   外部副作用。

-   相关配置和框架机制。

-   Go 与 Spring Boot 的已知差异。

-   已经执行的测试及其覆盖范围。

-   尚未确认的行为与证据缺口。

尽量保留已有文件路径、函数或方法位置、证据编号及原始结论引用。

如果已有分析提供了稳定的证据 ID，应优先引用该
ID，而不是复制整份报告。只有当原有证据无法支持当前结论时，才重新检查对应实现。

#### 41.3.2 明确每项结论的适用范围

每项被复用的结论，都必须能够回答：

-   它针对哪个执行单元？

-   它成立的前置条件是什么？

-   它确认的是局部行为，还是已经确认了与其他执行单元的交互？

-   它覆盖哪些输入、分支和失败情况？

-   它是否依赖某个特定配置或运行环境？

-   当前组合场景是否满足这些条件？

例如，某个局部操作在正常输入下可以正确返回结果，并不能直接证明它在被上游组件调用时一定得到相同输入，也不能证明下游组件会正确解释它的返回结果。

如果当前组合场景超出了已有结论的适用范围，应补充验证超出的部分，而不是重新复制整份单组件分析。

#### 41.3.3 禁止从局部结论推导未经验证的整体结论

以下推理均不成立：

-   每个组件分别通过，所以组合行为必然正确。

-   每个接口的请求结构相同，所以接口交互语义相同。

-   每个局部操作都正确，所以它们的执行顺序一定正确。

-   每个组件都能处理自己的错误，所以错误经过多个组件后一定被正确处理。

-   每个数据操作都成功，所以最终业务状态一定正确。

-   原有单组件测试通过，所以未覆盖的组合场景也已经通过。

Agent
必须明确指出：哪些整体结论已经有直接证据，哪些仍然需要通过组合分析或测试建立。

### 41.4 构建实际执行关系模型

在开展具体场景验证之前，先建立足以解释当前业务行为的执行关系模型。

该模型不是要求输出某种固定架构图，而是要求 Agent
能够从真实代码中解释：执行如何开始，关键数据和控制信息如何传递，状态如何变化，以及执行结果如何形成。

#### 41.4.1 追踪输入的来源与去向

对于影响当前业务结果的关键数据，追踪其来源、转换过程和使用位置。

需要回答：

1.  数据最初由谁提供或产生？

2.  数据进入系统后经过了哪些解析、校验、转换或补充？

3.  哪些执行单元读取了它？

4.  它是否被复制、覆盖、缓存、持久化或转换成另一种表示？

5.  哪个条件分支或状态变化依赖该数据？

6.  数据经过跨组件边界后，其含义是否发生变化？

7.  Go 与 Spring Boot
    是否对缺失值、默认值、空值或类型转换采用了不同处理方式？

8.  最终结果中的相关字段来自哪里？

只追踪对当前行为具有实质影响的数据，不要求罗列所有局部变量。

如果数据字段名称相同但业务含义可能不同，应分别确认其来源与用途；如果字段名称不同但实际表达同一语义，应根据真实数据流建立对应关系。

#### 41.4.2 追踪控制流与分支条件

对影响整体结果的关键控制分支，追踪其判断条件及后续路径。

需要回答：

-   分支由哪些输入、状态、返回值、错误或配置决定？

-   判断发生在什么位置？

-   判断成立和不成立时分别执行什么操作？

-   哪些后续步骤依赖该分支结果？

-   是否存在提前返回、异常中断、重试或降级路径？

-   Go 与 Spring Boot 的分支条件是否具有相同语义？

-   即使条件表达式不同，两边是否仍然覆盖相同的业务情况？

-   是否存在一边新增或遗漏某条实际可达路径的情况？

不得仅对照条件表达式的文本相似度。必须解释条件在业务上判断的是什么，以及两边在相关输入下会进入哪条路径。

#### 41.4.3 追踪状态变化

识别当前业务行为会读取或改变哪些实际状态。

状态可以来自任何真实存在的数据源或运行机制，例如持久化数据、共享状态、缓存、任务状态或外部系统中的记录。是否存在这些状态，必须由项目证据确认。

对于每项重要状态，记录：

-   初始状态从哪里读取。

-   哪些条件会影响后续处理。

-   哪个步骤负责修改状态。

-   修改是否立即生效。

-   修改失败时系统处于什么状态。

-   后续步骤依赖的是修改前还是修改后的状态。

-   多个操作之间是否存在一致性要求。

-   Go 与 Spring Boot 的执行顺序或状态处理是否存在差异。

不得只根据方法名称推测状态已经改变。需要追踪真实写入、事务边界或可靠的运行证据。

#### 41.4.4 追踪错误与副作用

将错误路径视为执行关系的一部分，而不是正常流程之外的附属说明。

对于可能影响最终结果的失败，追踪：

-   错误从哪里产生。

-   错误如何被返回、抛出、包装、转换或传播。

-   哪些调用方会接收到该错误。

-   哪些后续步骤因此被跳过。

-   哪些已经发生的副作用不会自动撤销。

-   是否存在重试、补偿、清理或其他恢复机制。

-   最终调用方看到的结果是否准确反映实际状态。

如果当前业务行为没有某类副作用或恢复机制，不需要为了填满分析而强行加入该类内容。

### 41.5 从实际逻辑中推导组合验证问题

组合验证的问题必须从已发现的执行关系中推导，而不是从预先准备的业务场景清单中挑选。

Agent
应当对每条重要交互关系提出以下问题，并根据实际代码决定哪些问题需要深入验证。

#### 41.5.1 输入与契约问题

-   调用方提供的信息是否满足接收方的实际前置条件？

-   接收方对输入的解释是否与调用方的预期一致？

-   必要字段是否可能缺失或在转换中丢失？

-   调用方是否使用了正确的返回字段？

-   接收方返回的默认值、空值或错误是否具有明确含义？

-   是否存在协议、类型或配置差异改变输入输出语义的情况？

#### 41.5.2 顺序与依赖问题

-   某个步骤是否依赖另一项操作已经成功完成？

-   该依赖是否由真实控制流或同步机制保证？

-   如果执行顺序改变，最终结果是否会变化？

-   是否存在提前返回绕过必要步骤的路径？

-   是否存在重复执行导致结果变化的路径？

-   多个步骤分别正确，但组合顺序可能违反业务约束吗？

#### 41.5.3 状态与一致性问题

-   多个执行单元是否读取或修改同一份业务状态？

-   一个执行单元的修改是否会改变另一个执行单元的判断？

-   状态检查与状态修改之间是否存在时间窗口？

-   局部操作成功后，后续操作失败会留下什么状态？

-   系统是否要求多个变化同时生效，还是允许部分成功？

-   这种要求是否有业务契约、现有实现或其他可靠证据支持？

#### 41.5.4 错误与恢复问题

-   某个执行单元失败后，上游和下游分别如何处理？

-   错误是否可能被忽略、覆盖或转换成不准确的结果？

-   重试是否会重复执行已经产生副作用的操作？

-   某个失败是否可能发生在不可自动撤销的操作之后？

-   系统是否提供恢复、补偿或最终一致性机制？

-   Go 与 Spring Boot 在同一失败条件下是否会留下不同的状态？

#### 41.5.5 可观察结果问题

-   调用方最终会看到什么响应、错误或状态？

-   最终响应是否与实际执行结果一致？

-   外部系统能否观察到不同的副作用？

-   相同业务输入是否可能因实现差异而进入不同的关键路径？

-   这些差异是否影响接口契约、业务约束或调用方行为？

以上问题是分析问题的生成方法，不是要求每个项目都必须逐条输出肯定或否定答案。只需深入当前执行关系中真实存在、可能影响结论的问题；对于排除的重要风险，应有足够证据支持排除理由。

### 41.6 根据真实逻辑构造验证场景

完成执行关系分析后，Agent 必须把重要的交互关系转化为可验证的场景。

场景的来源应当是实际代码分支、接口约束、状态依赖、错误处理和已识别风险。不得预先假定每个项目都必须包含某类业务操作、基础设施或失效场景。

#### 41.6.1 每个场景必须具备的要素

每个重要场景至少明确：

1.  **验证目的**：该场景要确认什么行为或排除什么风险。

2.  **前置条件**：输入、相关状态、配置和必要的运行条件。

3.  **触发过程**：哪些实际调用或事件会启动该行为。

4.  **关键执行路径**：会经过哪些执行单元和分支。

5.  **关键交互**：执行单元之间交换什么信息，如何影响后续行为。

6.  **预期结果的依据**：该预期来自什么业务规则、接口契约、原有行为或已确认的不变量。

7.  **实际结果**：Go 与 Spring Boot
    分别执行了什么，或者测试实际观察到了什么。

8.  **副作用**：系统状态或外部环境发生了什么变化。

9.  **判断依据**：哪些证据支持一致性或差异结论。

10. **未决问题**：如果无法得出结论，还缺少什么证据。

预期结果不能由 Agent
凭空创造。如果业务要求不明确，应将预期标记为待确认，并分别说明代码实际行为和业务判断所需的证据。

#### 41.6.2 如何选择需要验证的场景

优先考虑以下情况，但只有在实际项目中存在相应条件时才适用：

-   正常执行路径。

-   影响关键分支的输入边界。

-   跨组件契约中的重要约束。

-   上游与下游对同一结果存在不同解释的可能性。

-   关键步骤失败或提前退出的路径。

-   已经发生部分状态变化后出现失败的路径。

-   重试、重复执行或并发可能改变结果的路径。

-   依赖配置、框架机制或运行时约定的路径。

-   Go 与 Spring Boot 已发现实现差异所涉及的路径。

-   现有测试未覆盖、但对关键结论有实质影响的路径。

该优先级不是固定的测试目录。实际场景应根据代码和风险动态产生。

如果某个场景不适用于当前项目，应根据真实实现说明原因；如果是否适用仍无法确认，应标记为未知，而不是直接跳过。

#### 41.6.3 防止场景无限扩张

组合验证并不要求穷举整个项目的所有输入和执行时序。

Agent 应根据当前业务行为的边界，优先验证那些能够影响核心结论的交互关系。

对每个候选场景，说明它验证了哪项业务约束、哪条调用关系或哪种已识别风险。无法关联到实际执行逻辑、接口约束或明确风险的场景，不应仅为了扩大测试数量而加入。

当多个场景覆盖相同的执行路径和相同的风险时，可以合并；但不能为了减少场景数量而掩盖不同的失败边界、状态变化或错误传播方式。

------------------------------------------------------------------------

### 41.7 对照 Go 与 Spring Boot 的实际执行行为

在确认真实执行路径与验证场景后，分别重建 Go 与 Spring Boot
的行为，再对照其业务语义。

不得先假设两种实现的结构相同，也不得仅根据类名、方法名或文件位置建立映射。

#### 41.7.1 分别重建两种实现

对于每个重要场景，先独立回答：

-   执行从哪里开始。

-   进入每一步时满足什么条件。

-   使用了哪些输入和状态。

-   执行了哪些关键操作。

-   哪些结果决定后续分支。

-   哪些错误会中断或改变流程。

-   哪些副作用已经发生。

-   最终形成什么业务结果和外部可观察行为。

先确认实际行为，再建立 Go 与 Spring Boot 的对应关系。

如果某个步骤由框架隐式执行，应追踪实际配置、调用机制或可靠的框架语义；不能仅凭注解或框架名称假定行为已经发生。

#### 41.7.2 建立基于语义的对应关系

将两边承担相同业务职责的执行步骤建立对应关系。

对应关系允许以下情况：

-   一个 Go 函数对应多个 Java 方法。

-   多个 Go 函数的职责由一个 Java 执行单元承担。

-   显式实现的职责由 Java 框架机制承担。

-   两边使用不同的数据访问方式，但产生相同业务结果。

-   两边采用不同的错误表达方式，但对外语义相同。

-   两边存在不同的中间步骤，但这些步骤不会改变需要保持的业务语义。

这些情况都不能仅凭实现形式判定通过。必须确认其实际输入、行为、返回结果、状态变化和失败边界满足所需的业务语义。

#### 41.7.3 对照结果必须落实到具体行为

对于每项重要差异，至少说明：

-   Go 实际执行了什么。

-   Java 实际执行了什么。

-   两边在什么条件下出现差异。

-   差异是否改变后续控制流。

-   差异是否改变数据或状态。

-   差异是否改变最终响应或外部副作用。

-   当前结论由哪些证据支持。

不要只写"Java
使用了另一种实现方式"或"整体逻辑基本一致"。如果不能解释差异对实际行为的影响，就不能结束该项验证。

------------------------------------------------------------------------

### 41.8 判断差异是否影响业务语义

并非所有实现差异都是问题，也并非所有与 Go 一致的行为都是正确的。

每项差异都必须独立判断，不得使用笼统的"Java 更符合框架规范"或"Go
是原始实现"作为最终依据。

#### 41.8.1 先确认差异本身

准确描述两边实际发生的行为，避免使用带有预设判断的措辞。

例如，应说明两边在哪个输入条件下进入不同分支、返回什么结果或修改什么状态，而不是直接写"Java
的逻辑不合理"。

如果差异尚未得到源码或运行证据确认，应标记为推断或未知。

#### 41.8.2 再确认差异是否可观察

根据当前业务行为的实际边界，判断差异是否影响：

-   调用方得到的结果。

-   业务状态。

-   数据持久化或其他外部副作用。

-   后续操作是否执行。

-   错误含义与恢复行为。

-   权限或其他明确的业务约束。

-   调用方对系统行为的合理预期。

如果内部实现不同，但在已确认的相关条件下，所有与当前契约有关的行为都保持等价，可以将其判定为合理的实现差异。

如果只验证了部分条件，则只能对已经覆盖的条件作出结论，不得将有限范围内的等价扩大为整体等价。

#### 41.8.3 最后判断业务可接受性

当发现可观察差异时，进一步确认哪种行为符合业务要求。

证据可以来自明确的接口契约、业务规则、经过确认的系统不变量、测试断言或其他可靠的项目资料。

如果 Go 与 Spring Boot
的行为不同，但现有资料没有说明应该采用哪种行为，则应将业务可接受性标记为未知，并指出需要确认的具体规则。

如果 Go 与 Spring Boot
的行为相同，但两边都违反了明确的业务要求，应报告业务缺陷，不能因为迁移一致就判定整个业务行为正确。

如果 Java 的行为有意偏离
Go，则必须确认这种偏离的依据、影响范围和验收要求，不能仅凭 Agent
自己认为更合理就接受该差异。

------------------------------------------------------------------------

### 41.9 证据链与结论可信度

每个关键结论都必须能够从报告追溯到实际依据。

#### 41.9.1 证据来源

根据项目实际情况使用以下证据：

-   `[CODE]`：实际源码及相关分支。

-   `[CONFIG]`：实际配置与启用的运行机制。

-   `[CONTRACT]`：接口、协议或明确的业务契约。

-   `[TEST]`：测试代码及其实际断言。

-   `[RUNTIME]`：可重复的运行结果、日志或实验观察。

-   `[INFERENCE]`：由现有证据推导，但尚未直接验证的结论。

-   `[UNKNOWN]`：现有证据不足以确认的事项。

标签可以按需要组合。标签的作用是说明结论依据，而不是代替证据本身。

#### 41.9.2 跨组件结论必须具备完整证据链

当一个结论依赖多个执行单元共同完成某项行为时，不能只提供其中一个执行单元的代码。

应根据实际依赖关系，提供足以支持整个推理过程的证据。

例如，如果结论依赖"某个输入字段经过转换后决定下游分支"，则需要能够确认字段的来源、转换、接收方的使用方式以及分支结果。

如果结论依赖"某个失败不会产生副作用"，则需要检查可能产生该副作用的执行路径，而不能只引用最终返回错误的位置。

证据链不必覆盖无关代码，但必须覆盖从已确认事实到最终结论之间的关键推理步骤。

#### 41.9.3 明确区分事实、推断与未知

每项结论必须能够区分：

-   已由直接证据确认的事实。

-   基于事实推导出的结论。

-   尚未验证的假设。

-   因资料或运行条件不足而无法判断的问题。

不能将"源码中没有发现"直接表述为"系统绝对不会发生"；不能将"测试没有失败"直接表述为"所有相关行为正确"；不能把框架的理论能力直接当成当前项目已经启用的行为。

当证据相互冲突时，应保留冲突并继续调查，不能只选取支持预期结论的证据。

------------------------------------------------------------------------

### 41.10 测试与验证方法的选择

组合验证应根据待确认的问题选择适当的验证方法，不得预先规定所有项目都必须使用相同类型的测试。

#### 41.10.1 先明确测试需要证明什么

每个测试或实验都应对应一个明确的问题，例如：

-   某项输入是否会触发预期分支。

-   某个执行单元是否正确解释下游返回值。

-   失败后是否仍然执行某个操作。

-   某项状态变化是否与最终响应一致。

-   两种实现对相同条件是否产生不同结果。

-   某个框架配置是否实际改变了执行行为。

如果无法说明测试结果如何支持某个结论，就应重新审视测试设计。

#### 41.10.2 根据问题选择验证范围

根据需要选择静态代码分析、单元测试、跨组件集成测试、真实运行验证或其他适合的方法。

这些方法的证据能力不同。

例如，模拟下游返回值可以验证调用方对该返回值的处理，但不能单独证明真实下游一定会返回该值；静态检查可以确认某个分支的代码逻辑，但未必能证明运行环境中的配置或框架代理实际生效。

Agent 必须说明所采用的方法能够证明什么，以及仍然不能证明什么。

#### 41.10.3 测试缺失时不得直接判定通过

如果现有测试没有覆盖重要的交互关系，应判断是否需要补充测试或进行其他验证。

如果当前环境不允许执行测试，应说明限制、已有静态证据及未决风险。

如果测试通过但与代码分析不一致，应调查原因，不能以测试通过为由直接忽略源码证据，也不能未经调查就认为测试没有价值。

#### 41.10.4 不把所有未知问题都转化为测试

某些问题需要阅读契约、检查配置、理解框架调用机制或向业务规则负责人确认，并不一定能够通过增加测试直接解决。

Agent 应根据未知项的实际来源选择解决方式，而不是统一输出"建议增加测试"。

------------------------------------------------------------------------

### 41.11 最终结论的分类

每个重要验证对象和场景都必须分别形成迁移一致性结论与业务可接受性结论。

#### 41.11.1 迁移一致性

使用以下分类：

-   `EQUIVALENT`：已验证范围内的业务行为及相关可观察结果等价。

-   `IMPLEMENTATION_DIFFERENCE`：内部实现不同，但有充分证据支持其所需业务语义等价。

-   `OBSERVABLE_DIFFERENCE`：已确认存在可观察差异，但尚未确定是否违反业务要求。

-   `SEMANTIC_MISMATCH`：有充分证据证明 Go 与 Spring Boot
    在所需业务语义上不一致。

-   `UNKNOWN`：证据不足，无法可靠判断。

这些标签应当针对明确的行为、场景和验证范围使用，而不是不加区分地给整个项目贴一个标签。

#### 41.11.2 业务可接受性

使用以下分类：

-   `ACCEPTABLE`：现有证据支持该行为符合业务要求。

-   `UNACCEPTABLE`：有明确要求或不变量证明该行为不可接受。

-   `UNKNOWN`：缺少足够依据判断业务是否允许该行为。

迁移一致性与业务可接受性必须分开。

两边行为等价，不代表行为本身一定正确；两边行为不同，也不代表差异一定不可接受。最终结论取决于实际行为、适用契约和证据，而不是
Agent 的主观偏好。

------------------------------------------------------------------------

### 41.12 最终交付物

最终报告应当按照实际发现的验证对象组织，不要求采用固定的组件清单。

#### 交付物 A：验证范围与已有结论复用记录

说明：

-   本轮验证的业务行为和实际边界。

-   识别出的关键执行单元及交互关系。

-   复用的已有结论及其证据位置。

-   新发现的交互问题。

-   未纳入范围的部分及其理由。

-   当前仍然存在的证据缺口。

#### 交付物 B：实际执行关系与数据流

展示关键执行步骤、数据来源、数据转换、控制分支、状态变化和最终结果。

可以使用表格、调用链、时序图或其他适合的表达形式，但所有节点与关系都必须来自实际代码、配置、契约或运行证据。

不要求每次输出所有图表，只选择能够清晰解释当前问题的形式。

#### 交付物 C：组合场景与验证结果

每个重要场景至少记录：

-   场景的来源及验证目的。

-   前置条件和触发条件。

-   Go 的实际行为。

-   Java 的实际行为。

-   关键交互和状态变化。

-   最终可观察结果。

-   迁移一致性结论。

-   业务可接受性结论。

-   支撑结论的证据。

-   未决问题及其影响。

#### 交付物 D：差异与风险清单

按照实际发现的情况，分别列出：

-   已确认的语义不一致。

-   已确认的业务缺陷。

-   已确认且可以接受的实现差异。

-   尚未判断业务可接受性的可观察差异。

-   证据不足的未决问题。

-   已验证但存在明确覆盖边界的事项。

每项都应说明触发条件、实际影响、证据和下一步行动，而不是只给出严重程度或笼统建议。

#### 交付物 E：未决问题与后续验证建议

对于每个未决问题，说明：

-   当前缺少什么信息或证据。

-   它影响哪个行为或结论。

-   为什么现有证据不足。

-   应通过检查源码、配置、契约、测试、运行环境还是业务要求来解决。

-   解决该问题是否会改变当前验收结论。

如果不存在未决问题，应以实际验证结果为依据说明，而不是默认填写"无"。

------------------------------------------------------------------------

### 41.13 完成标准

本阶段是否完成，应由验证范围内的关键行为是否得到充分确认决定，而不是由报告长度、组件数量或测试数量决定。

完成前确认：

-   验证对象来自实际代码与行为依赖，而不是预设的组件清单。

-   已明确本轮验证的业务边界及其依据。

-   已复用已有结论，并确认其适用范围。

-   已追踪所有对关键结论具有实质影响的交互关系。

-   已分析相关数据流、控制流、状态变化和错误传播。

-   已根据真实逻辑推导并验证重要场景。

-   已分别重建 Go 与 Spring Boot 的实际行为。

-   已区分实现差异、可观察差异和业务语义不一致。

-   已将迁移一致性与业务可接受性分开判断。

-   关键结论具有可追踪的证据链。

-   已说明测试或其他验证方法的覆盖范围。

-   重要未知项已经解决，或被明确记录并说明其对验收的影响。

验证完成不要求所有行为都必须被判定为通过。如果发现缺陷、存在重大未决问题或证据不足，应如实报告当前状态。

如果部分验证已经完成，可以报告已确认的范围，但不能将部分结果扩大为整个业务链路已经通过。

------------------------------------------------------------------------

### 41.14 执行纪律

执行本阶段时，遵守以下原则：

1.  **先发现，再验证。** 先从实际代码识别执行单元、交互关系和业务边界，再确定验证对象。

2.  **先追踪，再判断。** 在形成结论之前，追踪必要的数据、控制流、状态变化和错误传播。

3.  **先确认局部行为，再分析组合行为。** 复用已有证据，但不把局部结论扩大到未经验证的范围。

4.  **从真实逻辑推导场景。** 不得将任何固定组件、基础设施、业务规则或失效场景强加给当前项目。

5.  **以语义建立对应关系。** 不要求 Go 与 Spring Boot
    的文件、函数、类或框架结构一一对应。

6.  **以证据判断差异。** 不得仅凭命名、代码风格、框架偏好或主观合理性判定正确与否。

7.  **明确区分事实和推断。** 证据不足时标记未知，并说明如何解决。

8.  **按风险确定深度。** 对影响整体结论的交互关系深入分析；对无实际依赖的内容不做无意义扩展。

9.  **不把报告完整性当成验证完整性。** 写满所有栏目不能替代真实证据。

10. **不把迁移一致性当成业务正确性的替代品。** 两个问题必须分别得到结论。

本阶段最终必须能够解释：

**当前业务行为实际由哪些执行步骤共同完成；这些步骤通过什么关系相互影响；关键输入、状态和错误如何跨越执行边界；组合后产生什么结果；Go
与 Spring Boot
在什么条件下表现相同或不同；每个判断由什么证据支持；尚未确认的部分是否影响最终验收。**
