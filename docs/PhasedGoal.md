# 后端简历项目工程能力验收标准

## 一、任务目标

请审查当前工作区中的完整后端项目，判断它是否已经达到适合作为求职简历项目的工程能力要求。

本次审查的目标不是证明项目已经达到成熟生产系统标准，而是验证：

1. 核心业务功能真实、完整且正确。
2. 项目具有合理的工程结构，能够构建、启动、测试和演示。
3. 关键业务规则、数据一致性及安全边界得到了合理处理。
4. 项目中具有技术含量的机制能够被解释和验证。
5. 已知缺陷及尚未验证的能力得到如实记录，不以生产级要求无限扩大整改范围。

必须区分：
- 实现存在：源码中存在相关实现。
- 实现正确：实现满足预期业务语义。
- 已验证：有实际执行的测试或运行结果作为证据。

不得仅凭类、注解、依赖、配置或文档声明认定功能正确。

本项目的目标是成为一个能够体现后端工程能力、经得起技术面试追问的个人项目，而不是在缺乏真实业务需求的情况下，建设完整的生产运维体系。

### P0：简历项目准入要求

以下要求必须满足，或存在明确、有限且不影响核心正确性的已知例外：

1. 核心业务链路能够真实运行，不存在关键功能仅有接口骨架、模拟数据或硬编码成功结果的情况。
2. 核心参数校验、业务规则、身份认证和必要的权限控制有效。
3. 关键数据能够正确持久化，事务边界合理，不存在已确认的严重数据丢失、重复处理或状态错误问题。
4. 核心失败路径具有明确行为，不会无声吞掉关键异常或返回误导性成功结果。
5. 项目能够按照实际项目说明完成构建、配置和启动。
6. 核心业务具有可以执行的自动化测试，且测试断言真实业务结果。
7. 项目具有清晰的主要模块职责，能够追踪核心调用链。
8. 关键配置和敏感信息没有明显的不安全处理方式。
9. 已知严重缺陷、无法验证的关键能力和运行前提得到明确记录。

P0 不要求每个模块都具备相同的测试深度，但不得以非核心模块尚未完善为由掩盖核心业务缺陷。

### P1：简历项目竞争力要求

重点选择项目实际包含的复杂机制进行验证：

- 服务间 RPC、服务发现与超时处理。
- 数据库事务、并发更新及幂等处理。
- 消息处理与最终一致性（仅在项目实际使用消息机制时）。
- 关键失败路径、重复请求和依赖不可用场景。
- 结构化日志、关键运行指标及问题定位。
- 有代表性的性能测试或资源使用分析。
- 重要方案的设计理由、适用边界和替代方案。

至少选择两到三个与项目技术方向密切相关的机制，形成源码分析、测试设计、实际验证和结果解释的完整闭环。

不得为了达到 P1 要求而强行给项目引入原本不需要的中间件或架构。

### P2：暂不作为简历项目阻塞条件

除非项目的实际业务需求明确要求，否则以下事项不应自动阻止项目通过简历项目验收：

- 完整生产级 SLO 与事故管理体系。
- 基于真实生产流量的容量规划。
- 定期灾难恢复演练及生产恢复记录。
- 完整灰度发布、自动回滚和多版本发布治理。
- 覆盖所有理论故障组合的穷尽式验证。
- 大规模集群、复杂多租户隔离或高级流量治理。
- 对所有模块进行全面架构重构。

这些能力可以记录为后续深化项，但必须区分真正影响核心正确性的问题与单纯尚未建设的高级工程能力。

## 三、审查范围与执行方式

### 阶段 A：建立项目事实

检查项目实际包含的服务、模块、主要业务职责、核心调用方式、持久化组件、构建方式及现有测试。

以实际源码为准，不得仅根据目录名称或 README 推断实现。

不需要先输出冗长的目录树或通用架构介绍。

### 阶段 B：选择核心业务链路

从项目现有功能中选择：

1. 一条核心业务链路。
2. 一条涉及关键数据写入或业务规则的链路。
3. 一条体现项目主要技术特点的复杂链路。

如果链路之间存在重叠，可以合并分析，但必须说明覆盖了哪些行为。

对于每条链路，追踪：

触发条件 → 入口 → 关键调用 → 数据变化 → 成功结果 → 失败结果 → 必要的资源清理。

必须说明每个关键组件的实际职责，而不是仅列出类名。

### 阶段 C：检查十二个工程维度

仍然检查以下全部维度：

1. 业务闭环与功能正确性。
2. 微服务边界与依赖治理。
3. 服务发现与 RPC 通信。
4. 超时、重试、熔断与故障隔离。
5. 数据一致性与持久化正确性。
6. 认证、授权与安全边界。
7. 性能、容量与资源管理。
8. 日志、指标、追踪与告警。
9. 测试覆盖与质量门禁。
10. 构建、部署、配置与发布。
11. 备份、恢复与灾难应对。
12. 可维护性与持续演进。

每个维度必须给出结论，但不要求所有维度都进行生产级深度审查。

每个维度分别标记：
- P0：是否满足简历项目准入要求。
- P1：是否具有足够的技术深度。
- P2：是否属于后续深化事项。
- 证据等级：源码、已执行测试、实际运行或生产运行证据。
- 已确认问题。
- 尚未验证的风险。
- 是否影响当前简历项目验收。

不适用的机制必须说明不适用原因，不能机械要求项目引入特定技术。

### 阶段 D：执行必要验证

优先执行低风险且可重复的验证：

- 项目构建。
- 核心业务测试。
- 关键数据写入与查询。
- 关键参数非法、业务失败及重复请求测试。
- 实际存在的 RPC、事务或并发机制的代表性测试。
- 必要的启动和配置检查。

记录实际命令、退出状态、关键输出及测试断言。

无法执行时说明原因和前置条件，不得虚构结果。

不要求为了完成本次验收而执行高成本全量压测、真实生产故障注入或灾难恢复演练。

### 阶段 E：问题分类

将发现的问题分为：

- P0 阻塞问题：影响核心业务正确性、数据安全、关键权限或基本可运行性，必须先修复。
- P1 重点问题：影响关键工程机制的可信度或项目的技术竞争力，应优先处理。
- P2 后续深化：不影响当前核心功能和简历项目准入的高级工程能力或一般改进。

必须区分已确认缺陷和待验证风险。

不得把缺乏证据直接写成实现错误，也不得将已确认的严重缺陷降级为普通优化项。

## 四、工作量控制规则

1. 优先验证已有实现，不要默认所有能力都需要重新开发。
2. 不要为了达到生产级标准而无限扩展任务。
3. 不要对所有文件逐一撰写长篇审查报告；只对核心链路、关键机制和实际问题进行深入分析。
4. 对普通模块，优先确认其功能是否成立、测试是否存在、是否有已知严重问题。
5. 对关键机制，深入分析调用链、失败行为、状态变化及测试证据。
6. 每发现一个问题，都必须说明它是否影响 P0、P1 或仅属于 P2。
7. 修复建议必须给出具体修改位置、预期行为和验收条件，不得只写“增加幂等性”“完善监控”等泛化建议。
8. 每轮只优先处理当前最重要且依赖条件已经满足的一组问题，不要在核心问题尚未解决时生成庞大的非必要重构清单。
9. 不要求所有工程能力都达到最高等级；但凡涉及核心业务正确性、安全或数据完整性，就不能因为项目属于个人项目而降低必要标准。

## 五、最终交付物

### 交付物 1：项目验收总览

说明：
- 项目主要功能和技术特点。
- P0 准入要求的满足情况。
- P1 技术深度的体现。
- 已确认的关键缺陷。
- 尚未验证的关键风险。
- 是否建议作为当前简历项目。
- 尚需完成的最小必要工作。

### 交付物 2：核心业务链路分析

对选定的核心链路，给出实际调用顺序、关键文件职责、数据变化、成功路径、失败路径和现有测试证据。

不需要将整个项目所有文件都展开到相同深度。

### 交付物 3：十二维度验收表

每个维度给出 P0、P1、P2 结论、证据等级、实际问题和是否影响当前验收。

### 交付物 4：问题清单

每个问题包含：
- 唯一编号。
- 问题类型和优先级。
- 涉及文件与实际证据。
- 触发场景。
- 当前行为与预期行为。
- 修复方向。
- 验收条件和测试方案。

### 交付物 5：最小可行实施计划

按照依赖关系安排：

第一阶段：修复 P0 阻塞问题。

第二阶段：补齐核心业务测试和关键失败路径。

第三阶段：完成两到三个代表性复杂机制的 P1 验证。

第四阶段：处理必要的构建、运行、日志和配置问题。

第五阶段：将 P2 事项单独列入后续深化清单。

每项任务必须关联问题编号，给出完成条件。不得在没有实际必要的情况下建议大规模重构。

## 六、最终判断原则

本次审查的成功标准不是项目获得最高成熟度评级，而是明确回答：

1. 这个项目现在能否作为简历项目。
2. 为达到准入要求，最少还必须做什么。
3. 哪些技术点已经有源码和测试证据支撑，可以用于面试讲解。
4. 哪些技术点只有实现，没有验证，不能夸大描述。
5. 哪些工作值得投入以提高求职竞争力。
6. 哪些高级工程能力可以暂时不做。

现在开始检查当前工作区的实际项目。先建立事实，再执行必要验证，最终给出明确的验收结论和有优先级的工作清单。不要先给出项目等级，不要只输出审查计划，也不要为了追求生产级完整性无限扩大工作范围。
