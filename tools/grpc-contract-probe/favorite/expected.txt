# 格式：case_id 	 kind 	 value

#          （code=...|desc=...|body=...|rhdr=...|rtrl=...）
#          ⇒ 它同时是「Go 真源变了探针立刻响」的哨兵 + 两侧比对的基准。
#
# kind 四档：
#   SAME      —— 两侧**逐字节相同**（status code / description / 消息字节 / metadata key）
#   SAME_CODE —— 两侧 **status code 相同**（语义等价），description 措辞允许不同
#   OBS       —— 两侧**必须不同**（已登记的框架/库层差异）⇒ 变成一样反而是回归
#   SKIP      —— 显式跳过，理由必须写在本文件里
#
# ⚠️ 业务用例的 rhdr 只保留**非 grpc-*} 的 key（理由见 README 第三节）。
#    grpc-* 的头由 gRPC 协议与传输库产生，不是 favorite 域的行为 ⇒ 被单独放进
#    c30_response_header_surface 这一个 OBS 用例里量化。
#
# ⚠️ SAME_CODE 的两条（c35 / c36）：两侧 **status code 都是 UNIMPLEMENTED**（语义一致），
#    但 description 措辞不同 ⇒ 属 gRPC 库层 ⇒ 只断言 code 相同，不断言文案相同。
#    ✅ **归因已于 2026-10-25 第十四轮查清并修正**（此前记的「Go 侧 unknown service
#    /favorite.FavoriteService（带前导斜杠）」是**探针自己把 :path 拼坏**造成的假象）：
#    · grpc-java 的 `MethodDescriptor.generateFullMethodName` = `service + "/" + method`
#      （**不**补前导斜杠），而 netty 客户端写 `:path` 时**自己补一个 "/"**
#      ⇒ 描述符若手写成 "/favorite.FavoriteService/DoesNotExist"，
#        线上路径就成了**双斜杠** "//favorite.…"。
#    · grpc-go v1.81.1 `server.go:1826` **只剥掉一个**前导 "/" ⇒ 它切出的 service 名
#      = "/favorite.FavoriteService"（带斜杠）⇒ 查注册表必然落空
#      ⇒ 误落到 `unknown service` 分支，而不是「已注册服务 + 未注册方法」的
#        `unknown method` 分支 ⇒ **措辞被探针自己污染**。
#    · 修正后（描述符不带前导斜杠）两侧测的是同一件事，真实库级差异是：
#      Go 对「未注册方法」说 `unknown method X for service Y`、对「未注册服务」说
#      `unknown service Y`（**两种措辞**）；grpc-java 两种情形**共用一种措辞**
#      `Method not found: <full method name>` ⇒ **grpc-java 丢掉了「方法 vs 服务」的区分**。
#    ⇒ 实证锚点：c34 的描述符本来就不带前导斜杠 ⇒ 线上路径合法 ⇒ 真源 go-zero 注册的
#      health 服务**正常应答**（body=hex:0801 = SERVING）⇒ 客户端确实会补斜杠。
#
# ⚠️ c30 必须排在写入用例之前（否则它读的收藏夹被改名用例改过 ⇒ updated_at 变成
#    「本次运行的时刻」⇒ 冻结值每次都不同 ⇒ 假红）。
