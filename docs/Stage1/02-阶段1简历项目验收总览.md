## 一 · 项目主要功能与技术特点

### 1.1 这是什么

**一个已废弃商用架构（Go + go-zero + GORM）的 Spring Boot 现代化迁移产物**，**不是**教学练手项目。

| 项 | 值 |
|---|---|
| 原始项目 | `Sea-RideTheWind_golang`（go-zero + GORM，**冻结只读**） |
| 交付物 | RAG（本仓）—— Spring Boot + MyBatis-Plus + domain/mapper/service 分层 + 幂等 DDL |
| 规模 | **38 个组件 + 1 个共享层**（10 api + 10 rpc + 8 common + 10 proto）· 共享层 73 类 / 14,804 行 |
| 业务域 | `users`（含 admin）· `article` · `comment` · `favorite` · `follow` · `like` · `message` · `task` · `hot` |
| 真理之源 | **Go**（2026-10-20 第三次切换）⇒ 行为差异**默认判 RAG 错** ⇒ **一个不会移动的源** |

### 1.2 技术特点（**都是实际在跑的机制，不是名词**）

| # | 特点 | 它在本项目里到底解决什么 | 怎么证明它真在跑 |
|---|---|---|---|
| **1** | **事务 outbox + 事实流 + 跨域投递** | 「业务成功但事件丢了」⇒ 把事件变成**同事务内的数据行** | 真 PG 双侧活体 ＋ 幂等键 `like_consume_inbox` ＋ 单调版本号 |
| **2** | **数据库级不可变信封** | 「应用层自觉」不足以保证事实不被改写 ⇒ 触发器是最后一道 | 触发器**形式 + 函数体属性**逐条双侧对比（timing/事件集/粒度/volatility/语言） |
| **3** | **go-zero 语义到 Spring 的逐条复刻** | `,string` int64、未知码回落、`rest.WithJwt` 分段、熔断**逐路由 latch**…… | **HTTP 端点 72 ≡ 72 · gRPC 方法 71 ≡ 71**（10 域）＋ 错误码逐字节对拍 **9 域** |
| **4** | **fail-closed 的密钥链** | 「空签名密钥可起栈 ⇒ token 可伪造」⇒ 缺变量/空串/未解析占位符**三种都要启动失败** | 真 `SpringApplication` + 真 ConfigData ⇒ 守卫**变异必红** |
| **5** | **机器可判定的语义基线** | 「跑绿 ≠ 对」⇒ 把基线做成**可机械校验**的 | 一致性门 15 组检查 ＋ per-lane 矩阵**机器生成** ＋ 每个新增守门都配**变异测试** |
| **6** | **数据层双向可重放** | 「迁移改了没人重跑」不可见 ⇒ 仓里的 `.sql` 在干净临时库**原样重放** ↔ 活库逐项对比 | **9 域实测一致** ＋ 变异（`target_id` 255→200 ⇒ 精确报 1 处） |

## 三 · P1 技术深度的体现（§2.1 · P1）

> **P1 要求**：至少选 **2~3 个**与项目技术方向密切相关的机制，形成「源码分析 → 测试设计 → 实际验证 → 结果解释」的完整闭环。
> **本项目取 3 个**（详见交付物 3）：**M1 JWT + fail-open 黑名单** · **M2 事务 outbox + 数据库级不可变** · **M3 幂等消费 + 事实流版本号**。

| P1 九项 | M1 | M2 | M3 |
|---|---|---|---|
| ① 解决什么具体问题 | 身份伪造 / 会话撤销 | 事件丢失 / 事实被改写 | 重复处理 / 版本乱序 |
| ② 为什么需要 | 分布式服务需可验证身份 | 应用层自觉不足以保证不可变 | Kafka 至少一次 ⇒ 必须幂等 |
| ③ 真实调用链 | 交付物 3 §A.2 | §B.2 | §C.2 |
| ④ 状态/数据变化 | §A.3 | §B.3 | §C.3 |
| ⑤ 正常工作 | §A.4 | §B.4 | §B.4 |
| ⑥ 失败表现 | 7 类错误码 | 触发器拒绝 | 幂等跳过 / 三段式分流 |
| ⑦ 如何证明 | 9 种 JWT 边界双侧活体 | 触发器形式 + 函数属性对比 | 29 码逐条 + 4/4 实跑 |
| ⑧ **适用边界** | 保护面未自动比对 | **函数体语义机器判不了** | **只保证不重复，不保证不丢** |
| ⑨ 进一步提高需改什么 | 保护面自动比对 | 函数体语义自动化 | 对账 / 补偿（阶段二） |

⇒ **P1 闭环成立**（三个机制都有完整九项闭环，**且都写明了边界与不足** ⇒ 不是「吹」出来的）。
⇒ **本项目的额外深度**（超出 P1 最低要求）：**「跑绿 ≠ 对」被做成机器纪律** —— 每个新增守门都配**变异测试**；一致性门**从基线里抓出过两处算术错误**（P0 汇总数错、§6.3 命令数错）；**守门本身也被审计**（锚点门实测 **52% 假阳性** ⇒ 改判据 ⇒ 数字从 56 降到 27）。
