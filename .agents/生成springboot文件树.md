# Go → Spring Boot：基于目标项目既有架构与框架职责推导理论 Java 文件树

## 一、任务

给定：

- 一个 Go 微服务中的指定 Component / RPC。

- 对应的 Go 源码、依赖组件及其实际运行路径。

- 一个采用 Spring Boot 风格组织代码的目标 Java 微服务。

- 目标 Java 项目现有的包结构、组件组织方式和框架配置。


你的任务是：

> 在理解 Go Component 实际职责、保留必要 L1–L3 语义并允许 L4 实现机制根据 Java 环境重新选择的前提下，结合目标 Spring Boot 项目已有的包结构与组件职责，推导该 Component 迁移后的理论 Java 文件树。

本任务的最终产物是一棵**按照目标 Spring Boot 项目组织方式推导出来的理论 Java 文件树**，而不是一棵与 Go 文件树相似的 Java 文件树。

本任务只负责推导理论文件树，不直接实施代码迁移，不修改任何源代码、配置或测试文件。

---

## 二、核心目标与限制

### 2.1 Go 决定迁移什么，Java 决定如何组织

必须区分三个问题：

1. Go Component 实际承担了哪些职责，哪些行为不能丢失？

2. 目标 Spring Boot 项目通常如何组织这些职责，哪些现有组件和框架机制可以直接复用？

3. 根据前两项，最终需要哪些 Java 文件，各自放在哪个包中，文件之间如何协作？


第一个问题由 Go 源码和实际依赖决定。

第二个问题由目标 Java 项目的真实代码、包结构、配置和框架用法决定。

第三个问题由前两个问题共同推导。

**不得将 Go 文件数量、名称或边界直接作为 Java 文件树的设计依据。**

### 2.2 不追求文件最少，也不追求文件对应

本任务不以减少 Java 文件数量为目标，也不要求保留 Go 的文件划分。

允许以下情况：

```
一个 Go 文件
    ↓
多个 Java 文件
```

```
多个 Go 文件
    ↓
一个 Java 文件
```

```
多个 Go 文件
    ↓
多个 Java 文件
```

```
一个或多个 Go 文件
    ↓
目标项目已经存在的 Java 组件
```

```
一个或多个 Go 文件
    ↓
Spring / Java 已有机制直接承担
    ↓
不需要新增 Java 文件
```

以上情况均可能合理，必须依据实际职责和目标项目的组织方式判断。

禁止预设：

- 一个 Go 文件必须对应一个 Java 文件。

- 一个 Go 文件的职责必须全部由同一个 Java 类承担。

- 多个 Go 文件的职责必须拆成多个 Java 类。

- Java 文件数量应当接近 Go 文件数量。

- Spring Boot 项目应当机械采用固定的 Controller → Service → Repository 三层结构。

- 只要某个 Go 文件被合并或消失，就代表迁移结果更好。


**文件数量不是正确性指标。职责是否完整、组件边界是否合理、是否符合目标项目的既有组织方式，才是判断依据。**

## 三、目标 Spring Boot 项目的既有包结构

目标项目已经形成以下包组织约定。理论 Java 文件树必须优先遵循这些约定，不得在没有依据的情况下重新设计另一套架构。

以下包名以实际模块根包为前缀，例如：

```
<base-package>.api.controller
<base-package>.rpc.service.impl
```

其中 `<base-package>` 代表目标项目实际使用的 Java 根包，不是需要原样创建的包名。

### 3.1 API 模块

```
api/
├── advice/
├── config/
├── dto/
├── metrics/
├── client/
├── controller/
├── interceptor/
└── service/
```

各包的职责如下。

|包|既有职责|推导时的判断依据|
|---|---|---|
|`api.advice`|统一处理 HTTP 响应和异常|是否存在需要统一处理的 HTTP 异常、响应封装或相关行为|
|`api.config`|存放配置类、配置绑定类|是否存在需要由 API 模块使用的配置或组件装配|
|`api.dto`|存放 HTTP 请求和响应的数据对象|HTTP 接口实际需要接收、返回或转换哪些数据|
|`api.metrics`|存放业务监控指标|当前业务是否存在需要采集的指标及其记录时机|
|`api.client`|存放下游 RPC 客户端|API 业务是否需要调用下游 RPC 服务|
|`api.controller`|存放 HTTP 请求入口|哪些 HTTP 接口需要对外提供，入口处理包含哪些职责|
|`api.interceptor`|存放请求拦截、JWT 鉴权逻辑|哪些请求拦截、身份认证及相关处理需要在此层实现|
|`api.service`|存放业务用例及相关辅助组件|API 层需要执行哪些业务用例，哪些辅助组件属于 API 层职责|

### 3.2 RPC 模块

```
rpc/
├── bootstrap/
├── config/
├── domain/
├── exception/
├── mapper/
├── metrics/
└── service/
    └── impl/
```

各包的职责如下。

|包|既有职责|推导时的判断依据|
|---|---|---|
|`rpc.bootstrap`|存放应用启动时执行的初始化、注册和校验逻辑|是否存在启动阶段必须执行的初始化、注册或校验|
|`rpc.config`|存放配置绑定类和配置类|是否存在 RPC 模块所需的配置、Bean 定义或组件装配|
|`rpc.domain`|存放数据库实体类|数据持久化需要哪些实体及其映射关系|
|`rpc.exception`|存放自定义业务异常|是否需要定义业务异常及其传播、转换方式|
|`rpc.mapper`|存放数据库访问接口和 SQL 操作|数据查询、插入、更新、删除及相关持久化操作如何组织|
|`rpc.metrics`|存放业务监控指标|RPC 业务有哪些指标、记录条件和统计行为|
|`rpc.service`|存放业务逻辑和 gRPC 服务实现|RPC 业务用例、领域处理及服务相关组件如何组织|
|`rpc.service.impl`|存放 gRPC 接口实现类|哪些类负责实现实际的 gRPC 服务接口|

以上包结构是目标项目的既有组织约定，不是要求每个包都必须创建文件。

当前 Component 不需要某项职责时，不得为了填满目录而创建空类、占位类或无实际用途的组件。

### 3.3 包结构的使用规则

必须遵循以下原则：

1. 优先将职责放入目标项目已有的对应包。

2. 不得因为 Go 中存在同名职责，就在 Java 中创建同名类。

3. 不得因为某个 Go 文件承担多种职责，就要求这些职责全部进入同一个 Java 包。

4. 不得因为某个 Go 文件承担单一职责，就要求 Java 必须为它保留独立文件。

5. 不得为了保留 Go 的文件边界而在现有包结构之外随意增加 `handler`、`logic`、`repository`、`middleware`、`servicecontext`等 Go 风格目录。

6. 如果目标 Java 项目已经存在可以承担某项职责的组件，应优先评估复用，而不是重复创建。

7. 如果目标项目的实际代码与上述包职责说明存在差异，应检查实际代码，并明确指出差异；不得静默忽略已有架构，也不得无依据地自行改变架构。

8. 如果某项职责确实无法合理归入现有包，先说明具体职责、现有包无法承载的原因以及目标项目中的实际依据，再提出必要的新增包。不得仅因为 Go 中有相应文件就新增目录。

## 四、L1–L4 语义约束

推导理论文件树时，必须区分哪些行为需要保留，哪些实现机制可以根据 Spring Boot 的能力重新选择。

### 4.1 L1：外部契约

包括实际对外暴露的接口契约，例如：

- HTTP 路由、请求方式及接口输入输出。

- RPC 方法、请求与响应契约。

- 字段的外部含义、可选性、默认值及约束。

- 状态码、错误码及可观察的错误表达。

- 外部调用方依赖的行为。


具体项目中不存在的契约不必强行列出。

### 4.2 L2：业务语义

包括：

- 业务规则和条件分支。

- 状态转换及业务约束。

- 身份认证与权限判断所要求的业务结果。

- 数据读写的业务含义。

- 操作顺序及前置条件。

- 成功、失败、拒绝和部分成功的业务含义。

- 缓存、消息、RPC 等外部交互所影响的业务行为。

- 业务副作用及其触发条件。


不能因为 Java 使用了不同的类、注解、调用方式或框架组件，就认为这些业务语义可以被省略。

### 4.3 L3：影响可观察行为的技术语义

包括实际影响系统行为的技术约束，例如：

- 事务边界和原子性。

- 错误传播、异常转换及失败处理。

- 超时、重试和降级。

- 幂等性与重复请求处理。

- 并发控制及状态一致性。

- 缓存一致性及失效行为。

- 序列化和反序列化行为。

- 资源生命周期及清理。

- 消息投递、消费及确认行为。

- 调用顺序和副作用发生的先后关系。


仅分析当前 Component 实际涉及的技术语义，但不能跳过源码中真实存在的分支和异常路径。

### 4.4 L4：可重新选择的实现机制

包括可以根据 Java/Spring 现有能力重新组织的实现方式，例如：

- 依赖注入与依赖持有。

- 配置绑定和配置装配。

- 请求拦截与通用鉴权基础设施。

- 组件注册与生命周期管理。

- 代码组织和文件划分。

- 通用框架适配与样板代码。

- 可以由目标项目已有组件直接承担的基础设施工作。


L4 允许改变实现方式，但不能借此改变必要的 L1–L3 行为。

**不能把“实现方式可以改变”解释为“原实现中的职责可以省略”。**

## 五、第一阶段：研究目标 Java 项目

在推导任何新 Java 文件之前，先检查目标 Java 项目的实际代码和组织方式。

至少检查与当前 Component 相关的：

1. API 与 RPC 模块的实际包结构。

2. 现有 Controller、Service、DTO、Client、Interceptor 等组件。

3. gRPC 服务接口与实现类的组织方式。

4. 现有数据库实体、Mapper 和 SQL 操作方式。

5. 配置绑定、Bean 注册、依赖注入和组件装配方式。

6. 统一异常处理及业务异常定义方式。

7. 现有 JWT 鉴权、请求拦截及身份上下文处理方式。

8. 业务指标采集与记录方式。

9. 应用启动、初始化、服务注册和启动校验方式。

10. 现有组件之间的调用关系和职责边界。


只需要深入检查与当前 Component 的推导相关的部分，不要求无目的地审计整个仓库。

### 5.1 必须区分三种依据

分析过程中明确区分：

- **实际存在的项目约定**：能够在目标项目代码、配置或其他实际实现中找到证据。

- **本任务给定的包职责约定**：本 Prompt 中明确提供的目录用途。

- **推导建议**：现有代码和约定不能完全决定，但为完成理论文件树而提出的合理方案。


不得把推导建议伪装成目标项目已经采用的结构。

不得仅凭目录名称认定某项功能已经实现；必须在需要复用的情况下检查对应组件的实际职责。

## 六、第二阶段：分析 Go Component 的实际职责

以 Go 源码为行为和职责依据，识别当前 Component 的完整职责。

不要先将每个 Go 文件翻译成 Java 文件。此阶段只需要确定 Go 中实际存在什么，以及哪些职责必须迁移。

### 6.1 分析范围

根据当前 Component 的实际情况，检查：

- 对外入口和请求处理。

- 请求校验与参数转换。

- 业务用例与业务规则。

- 条件分支及状态转换。

- 数据库访问与持久化行为。

- 缓存读写及一致性行为。

- 下游 RPC 调用。

- 消息生产与消费。

- 身份认证、授权及请求上下文。

- 异常处理与错误转换。

- 事务和原子性。

- 业务指标及其记录条件。

- 配置读取和依赖使用。

- 启动初始化、注册和校验。

- 资源生命周期和清理。

- 与当前 Component 相关的其他实际职责。


只列出源码中真实存在或由依赖明确提供的职责。

如果某项能力不存在，不得为了使检查表完整而假设其存在。

### 6.2 按文件追踪，但不按文件划分 Java

列出当前 Component 实际涉及的 Go 文件，并对每个文件分析：

```
文件：
主要职责：
调用方：
调用的组件：
输入：
输出：
修改的状态：
产生的副作用：
处理的异常：
需要保留的业务语义：
可以改变的实现机制：
```

以上字段根据实际情况填写。

这一阶段逐文件分析，是为了防止遗漏源码中的职责、分支和异常路径。

**逐文件分析不代表逐文件映射。分析粒度与最终 Java 文件粒度是两个独立问题。**

### 6.3 不要把文件名当作职责证据

例如：

- `handler.go` 不一定只包含入口处理。

- `logic.go` 不一定只包含业务规则。

- `repository.go` 不一定只包含数据库访问。

- `middleware.go` 不一定只包含通用请求拦截。

- `servicecontext.go` 不一定只包含依赖持有。

- `types.go` 不一定只包含可以直接映射为 DTO 的类型。


必须检查实际源码，识别一个文件中是否混合了多个职责，以及一个职责是否分散在多个文件中。

## 七、第三阶段：建立职责映射，而不是文件映射

完成前两阶段后，将 Go 中需要保留的职责映射到目标 Spring Boot 的包、现有组件或实际框架机制。

此阶段是整个任务的核心。

### 7.1 每项职责都要有明确去向

对每一项实际识别的职责，判断它属于以下哪种情况：

**A. 由目标项目现有组件承担**

例如，目标项目已有的异常处理、配置组件、客户端、Mapper 或指标组件已经承担对应职责。

此时应明确指出实际复用的组件及其承担的职责，不应为了对应 Go 文件而重复创建组件。

**B. 由 Spring / Java 现有框架机制承担**

例如，依赖注入、配置绑定、请求过滤、应用生命周期等机制可以承担原来由 Go 显式代码完成的工作。

必须确认该机制确实能够承担当前职责，而不是只因为框架具有相关功能就假定它已经完成。

**C. 需要新建 Java 组件**

目标项目没有可直接复用的组件或机制，且当前职责需要 Java 代码实现时，才提出新文件。

新文件应根据目标项目的包职责和组件边界确定位置及名称。

**D. 需要拆分到多个 Java 组件**

当一个 Go 文件包含多个在目标 Java 项目中应分别承担的职责时，可以拆分到不同组件。

例如，通用请求拦截机制可以交给现有拦截器，而 RPC 特有的业务判断由业务服务承担。

**E. 可以由同一个 Java 组件承担**

当多个 Go 文件的职责在目标 Java 项目中属于同一组件的合理职责范围时，可以合并组织。

但必须根据实际组件职责、调用关系和项目惯例判断，不得仅为了减少文件数量而合并。

### 7.2 合并文件的判定规则

多个 Go 文件的职责可以由同一个 Java 文件承载，但不能只因为它们：

- 位于同一个 Go 目录。

- 被同一个上层函数调用。

- 都与同一个 RPC 有关。

- 在 Java 中都可以写进一个类。

- 都属于业务逻辑。

- 合并后文件数量更少。


就直接合并。

合并时应检查：

1. 这些职责是否属于同一组件的合理职责范围。

2. 是否具有一致的变化原因。

3. 是否需要独立的生命周期或依赖边界。

4. 是否存在独立的调用方、复用需求或接口契约。

5. 是否与目标 Java 项目现有组件的组织方式一致。

6. 合并后是否会让某个组件承担明显不同的职责。

7. 合并是否会使原有的业务规则、异常处理、状态管理或副作用难以明确定位。


不要求每一项都必须独立成文件，也不要求每一项都必须分开。最终结论必须与实际职责相符。

### 7.3 拆分文件的判定规则

一个 Go 文件可以拆成多个 Java 文件。

例如，当原文件同时包含：

- HTTP 请求入口。

- 请求与响应的数据结构。

- 业务用例。

- 下游调用。

- 业务指标记录。


目标 Spring Boot 项目可能分别使用 Controller、DTO、Service、Client 和 Metrics 组件承担这些职责。

但不得因为这些包存在，就机械地为每一种职责创建一个新文件。

只有当当前 Component 确实需要对应组件，且目标项目的职责边界支持这种划分时，才将其纳入理论文件树。

### 7.4 禁止机械地套用 Go 文件名称

不得仅根据 Go 文件名称创建以下 Java 文件：

```
Handler.java
Logic.java
Repository.java
Middleware.java
ServiceContext.java
Types.java
```

这些名称并非绝对禁止，而是不能将它们作为默认映射结果。

如果目标项目确实有对应的组件职责和命名约定，可以使用相应名称；否则应采用目标项目实际的包结构和命名方式。

## 八、第四阶段：识别 Spring Boot 可以直接承担的职责

必须区分两种变化。

### 8.1 Framework Absorption：框架职责吸收

Go 代码显式实现了某项基础设施或机制，而目标 Spring Boot 环境中的实际框架机制可以直接承担相同职责。

例如，Go 中存在用于保存依赖引用、传递配置和组装客户端的 `servicecontext.go`，而目标项目已通过 Spring Bean 和依赖注入完成这些工作。

在确认没有额外业务职责需要迁移后，可以不创建 `ServiceContext.java`。

其他可能需要检查的职责包括：

- 依赖持有与注入。

- 配置绑定和读取。

- 应用启动生命周期。

- 通用请求拦截。

- 通用身份认证。

- 通用异常处理。

- 服务实例注册。

- 其他目标项目已有机制直接承担的基础设施工作。


以上只是检查方向，不代表这些职责在目标项目中必然已经实现。

### 8.2 Existing Component Reuse：现有组件复用

Go 中某项职责在 Java 中仍然需要实现，但目标项目已经有组件承担它。

例如，Go 中存在数据库访问逻辑，而目标项目已经有相应的 Mapper 和 SQL 操作实现。

这不属于框架自动吸收，而是由现有业务或基础组件复用。

必须分别标记：

- `ABSORB`：由实际存在的框架机制直接承担。

- `REUSE`：由目标项目现有组件承担。

- `NEW`：需要新增 Java 文件。

- `SPLIT`：职责拆分到多个承载位置。

- `MERGE`：多个来源的职责由同一个 Java 组件共同承担。

- `ADAPT`：职责仍需实现，但实现方式需要适配目标 Java 环境。


### 8.3 不得扩大框架吸收范围

一个 Go 文件的一部分职责被 Spring 吸收，不代表整个文件都可以不再有对应的职责承载。

例如：

```
middleware.go
├── 通用身份认证
├── 通用权限检查
└── 当前 RPC 特有的业务判断
```

如果目标项目的拦截器或 Spring Security 机制已经承担前两项职责，而最后一项仍然影响业务结果，则应当：

- 将通用认证与权限机制交给实际承担它们的组件。

- 为特有业务判断确定明确的 Java 承载位置。

- 不得仅因为通用中间件可以被吸收，就把整个 Go 文件涉及的职责全部删除。


判断对象始终是实际职责，而不是文件名称。

## 九、第五阶段：按目标 Spring Boot 结构生成理论文件树

完成职责识别、目标架构研究和职责映射后，才开始生成最终 Java 文件树。

### 9.1 API 模块的推导规则

根据实际业务需要，考虑以下包：

- `api.advice`

- `api.config`

- `api.dto`

- `api.metrics`

- `api.client`

- `api.controller`

- `api.interceptor`

- `api.service`


具体规则：

**Controller**

承载 HTTP 请求入口，以及符合目标项目约定的入口处理职责。

不要为了复刻 Go Handler 而创建多个没有必要的 Controller，也不要把本应由其他组件承担的业务职责全部塞进 Controller。

**DTO**

承载 HTTP 请求和响应的数据对象。

不要直接按照 Go 的每个结构体文件机械生成 DTO。应当根据实际 HTTP 契约、数据用途及目标项目的 DTO 组织方式决定需要哪些类型。

如果请求与响应存在不同的契约或校验要求，应根据实际需要分别组织，不能为了减少文件而强行合并。

**Service**

承载 API 层的业务用例及相关辅助组件。

如果多个 Go 文件中的职责共同组成同一个业务用例，可以由目标项目中的同一个 Service 或相关组件承担；如果职责边界不同，则应根据目标项目实际惯例拆分。

不要因为 Go 存在 `logic.go` 就创建 `Logic.java`，也不要因为存在 Service 包就将所有职责一律归入某个 Service。

**Client**

承载 API 层需要使用的下游 RPC 客户端。

如果目标项目已有对应客户端，应优先复用；只有在缺少所需能力时才提出新文件。

**Interceptor**

承载目标项目约定的请求拦截和 JWT 鉴权相关职责。

必须区分通用鉴权机制与业务授权判断。不能把所有权限相关逻辑一律交给 Interceptor，也不能重复实现已有的鉴权机制。

**Advice**

承载需要由统一 HTTP 异常处理或响应处理机制承担的职责。

不能因为 Go 中有异常或错误处理代码，就逐个创建对应的 Java Advice 类。

**Config**

只纳入当前 Component 实际需要的配置类、配置绑定类或 Bean 配置。

已经由目标项目现有配置承担的内容不应重复创建。

**Metrics**

按照目标项目现有指标组件的组织方式承载实际需要的业务指标及其记录逻辑。

如果指标采集只是由现有公共机制完成，不要为了对应 Go 文件而重复创建指标类。

### 9.2 RPC 模块的推导规则

根据实际业务需要，考虑以下包：

- `rpc.bootstrap`

- `rpc.config`

- `rpc.domain`

- `rpc.exception`

- `rpc.mapper`

- `rpc.metrics`

- `rpc.service`

- `rpc.service.impl`


具体规则：

**Bootstrap**

承载应用启动阶段实际需要的初始化、注册和校验职责。

如果目标项目的启动流程、Bean 生命周期或注册机制已经承担对应职责，不要仅为了对应 Go 的初始化文件而创建新的 Bootstrap 类。

但如果仍有 RPC 特有的启动校验或初始化逻辑，就必须确定其承载位置。

**Config**

承载 RPC 模块实际需要的配置绑定和配置类。

不得仅根据 Go 的配置结构体逐个创建 Java 配置类；应当检查目标项目的配置约定、配置来源和实际使用方式。

**Domain**

承载数据库实体及其必要的映射定义。

不能将 Go 的每个数据结构都直接映射为数据库实体，也不能因为多个 Go 结构体字段相似就直接合并实体。必须根据实际持久化用途判断。

**Mapper**

承载数据库访问接口及 SQL 操作。

需要保留的查询条件、更新行为、持久化约束和结果语义都必须有明确承载位置。

如果目标项目已有可直接复用的 Mapper 或持久化组件，应优先评估复用。

不要因为 Go 中存在 `repository.go` 就默认创建同名 Repository，也不要因为使用 MyBatis 就假定所有原有持久化语义都自动得到保留。

**Exception**

承载目标项目需要定义的业务异常。

如果目标项目已有统一异常体系，应当优先遵循；不能为 Go 的每个错误返回路径机械创建异常类，也不能把不同业务含义的错误不加区分地合并。

**Metrics**

承载 RPC 业务实际需要的指标定义及记录逻辑。

必须保留实际指标的触发条件、记录时机和统计含义，不得只创建一个空的 Metrics 类。

**Service**

承载 RPC 业务逻辑和服务相关组件。

根据实际职责决定业务用例、辅助组件及其边界。不得机械地将 Go 的 `logic.go`、`service.go` 等逐一映射到同名 Java 类。

**Service/Impl**

承载实际的 gRPC 接口实现类。

根据当前 Component 实际暴露的 gRPC 接口决定需要哪些实现类。不能为了对应 Go 文件数量而创建额外实现类，也不能将多个独立 RPC 的实现随意合并。

### 9.3 API 与 RPC 之间的职责边界

必须结合目标项目的实际调用关系判断一项职责属于 API、RPC，还是由其他现有组件承担。

不能仅因为某项业务规则最初写在 Go 的 Handler 或 Logic 中，就直接决定其归属。

例如，同一个业务场景可能涉及：

```
HTTP Controller
    ↓
API Service
    ↓
下游 RPC Client
    ↓
gRPC Service 实现
    ↓
RPC Service
    ↓
Mapper
```

以上仅用于说明职责可能分布在不同组件中，不代表每个 Component 都必须创建完整链路中的所有文件。

如果实际调用链不同，应按真实调用链推导。

需要明确区分：

- HTTP 请求入口职责。

- API 层业务用例。

- 下游 RPC 调用。

- gRPC 服务入口。

- RPC 层业务逻辑。

- 持久化职责。

- 通用框架机制。


不得将同一项职责重复放入多个组件，也不得因为职责在调用链上经过多个组件，就认为每个组件都必须重新实现这项职责。

## 十、如何判断是否需要新增 Java 文件

新增文件必须具有明确的职责依据。

对每个拟新增的 Java 文件，回答：

1. 文件的主要职责是什么？

2. 当前 Component 为什么需要这项职责？

3. 这项职责在 Go 中有哪些实际实现依据？

4. 目标 Java 项目中是否已有组件承担该职责？

5. Spring / Java 是否已经直接承担该职责？

6. 为什么不能合理地放入现有 Java 组件？

7. 这个文件属于哪个既有包，其位置是否符合目标项目约定？

8. 如果与其他职责放在同一个组件中，是否会破坏合理的职责边界？

9. 如果单独创建文件，是否存在真实的职责、依赖、生命周期或接口边界依据？

10. 该文件是否只是为了对应某个 Go 文件而产生？


如果唯一依据是“Go 中有一个这样的文件”，不得直接创建 Java 文件。

如果目标项目已有组件可以承担职责，应优先评估复用。

如果现有组件不适合承担职责，应说明原因，再决定是否新增文件。

**新增文件需要有职责依据，但不要求它必须与某个 Go 文件一一对应。**

---

## 十一、如何判断是否可以不新增 Java 文件

对于每一项不再单独创建 Java 文件的职责，必须判断它属于以下哪种情况：

- 被 Spring / Java 框架直接承担。

- 被目标项目已有 Java 组件承担。

- 被合并到另一个职责边界合理的 Java 组件中。

- 被拆分到多个 Java 组件中。

- 当前 Component 实际不需要该职责，且有明确的源码或调用链依据。

- 暂时无法确定。


不得将以上情况全部笼统地标记为 `ABSORB`。

特别是：

**一个 Go 文件不再对应独立 Java 文件，与其中的职责已经被 Spring 吸收，是两个不同的结论。**

例如，多个 Go 文件的职责可以合并到同一个 Java Service 中，但这属于文件组织方式的变化，不代表这些业务职责被框架吸收。

同样，一个 Go 文件的职责可能被分配到已有的 Controller、Client 和 Service 中。这是职责拆分和现有组件复用，不代表原文件中的职责消失。

如果某项职责没有明确承载位置，不能仅因为它不再需要独立文件，就认为它已经得到处理。

---

## 十二、理论文件树的具体输出要求

最终输出必须包括以下部分。

### 12.1 第一部分：目标 Java 项目组织依据

简要列出与当前 Component 有关的既有包结构、组件职责和框架机制。

格式：

```
现有包：
已有组件：
已确认的框架机制：
当前 Component 可以直接复用的能力：
需要进一步确认的组织约定：
```

只列出实际检查到或由本任务明确提供的内容。

如果没有检查某项能力，不得声称该能力已经存在。

### 12.2 第二部分：Go 原始文件树

列出当前 Component 实际涉及的 Go 文件和必要的相关依赖文件。

只列出与当前 Component 的行为、职责或调用链有关的文件，不必输出整个 Go 仓库的无关目录。

格式示例：

```
Go Component/
├── handler.go
├── logic.go
├── middleware.go
├── repository.go
└── servicecontext.go
```

示例仅用于展示格式，实际结果必须来自目标源码。

### 12.3 第三部分：Go 文件职责分析

对每个实际相关的 Go 文件说明：

```
文件：
主要职责：
关键调用关系：
涉及的业务语义：
涉及的实现机制：
需要保留的行为：
可由 Java/Spring 替换的机制：
```

此处的目的在于确保 Go 的职责被完整识别，而不是建立一一对应的 Java 文件清单。

### 12.4 第四部分：职责到 Java 的映射表

必须使用以下格式：

|Go 来源及职责|Java 目标包或现有机制|承载方式|依据与原因|
|---|---|---|---|
|实际 Go 文件中的某项职责|实际目标包、现有组件或框架机制|NEW / REUSE / ABSORB / SPLIT / MERGE / ADAPT|说明职责为何这样组织|

要求：

- 一行对应一项实际职责，不要求一行对应一个 Go 文件。

- 一个 Go 文件可以出现多行。

- 多个 Go 文件可以映射到同一个 Java 组件。

- 一个 Go 文件的不同职责可以进入不同包。

- 已由现有组件承担的职责必须明确指出复用对象。

- 被框架吸收的职责必须明确指出实际承担机制。

- 不能确定的部分标记为 `UNKNOWN`，不得猜测。


### 12.5 第五部分：理论 Java 文件树

这是最终核心产物。

使用实际 Java 根包及目标项目既有的目录组织方式，例如：

```
<base-package>/
├── api/
│   ├── controller/
│   ├── dto/
│   ├── client/
│   ├── service/
│   └── interceptor/
└── rpc/
    ├── domain/
    ├── mapper/
    └── service/
        └── impl/
```

以上仅是结构示例，不是要求每次都生成这些目录或文件。

必须列出当前 Component 实际需要的新 Java 文件，并对每个文件简要说明：

```
文件名：
所属包：
主要职责：
承载哪些 Go 职责：
为什么需要独立文件：
依赖或调用哪些现有组件：
```

如果多个 Go 文件的职责合理地由同一个 Java 文件承担，应直接列出这个 Java 文件，并说明合并依据。

如果一个 Go 文件的职责被拆分到多个 Java 文件，应分别列出这些文件及各自承担的职责。

如果某项职责由目标项目已有组件承担，不要将其伪装成新文件；在文件树说明之外，明确列出所复用的现有组件。

如果某项职责由 Spring / Java 机制直接承担，不要为了对应 Go 文件而创建额外 Java 文件。

**最终文件树应当反映 Java 的组织方式，而不是用 Java 目录重新描绘 Go 文件树。**

### 12.6 第六部分：文件变化表

使用以下格式：

|Go 来源文件|Java 理论文件或现有机制|关系|原因|
|---|---|---|---|
|实际 Go 文件|实际 Java 文件或已有机制|KEEP / ADAPT / ABSORB / REUSE / SPLIT / MERGE|说明职责如何承载，以及文件边界为何变化|

关系定义：

- `KEEP`：该职责在 Java 中仍需要独立的代码载体，且保留独立文件符合目标项目的组织方式。

- `ADAPT`：该职责仍需实现，但需要适配 Java/Spring 的实现方式。

- `ABSORB`：该职责由实际存在的 Spring / Java 框架机制直接承担。

- `REUSE`：该职责由目标项目已有 Java 组件承担。

- `SPLIT`：同一 Go 文件中的不同职责分配到多个 Java 组件。

- `MERGE`：多个 Go 文件中的职责由同一个 Java 组件共同承担。

- `UNKNOWN`：现有证据不足，暂时不能确定。


这些关系描述职责迁移和文件组织的变化，不是强制的一对一映射规则。

不要为了填满表格而制造 Java 文件。也不要把所有不新增文件的情况都标记为 `ABSORB`。

### 12.7 第七部分：职责覆盖与组织合理性检查

必须逐项检查：

- Go 中所有需要保留的 L1 外部契约均已识别。

- Go 中所有需要保留的 L2 业务语义均有明确承载位置。

- Go 中所有影响行为的 L3 技术语义均有明确承载位置或实现方案。

- 所有实际业务分支和重要异常路径均已纳入职责分析。

- 所有被框架吸收的职责都有真实的机制依据。

- 所有复用的 Java 组件都已明确指出。

- 所有新增 Java 文件都有明确的职责依据。

- 所有合并的文件都有符合目标项目的组织依据。

- 所有拆分的文件都能解释职责边界。

- 没有仅为对应 Go 文件而创建的 Java 文件。

- 没有为了减少文件数量而不合理地合并组件。

- 没有把未实现的业务职责误判为框架吸收。

- 没有将目标 Java 项目尚未实现的能力描述成现有机制。

- 所有无法确认的组织决策都已标记为 `UNKNOWN`。


如果某项检查不通过，必须明确指出具体问题，不能仅输出“整体符合要求”。

## 十三、分析过程中的证据与判断要求

所有关键判断必须能够追溯到实际依据。

### 13.1 可以使用的依据

- Go 源码中的实际实现。

- Go Component 的调用链和依赖关系。

- Java 项目中的实际类、方法和调用关系。

- Java 配置、Bean 定义、框架注册和组件装配。

- 目标项目已有的包职责约定。

- 实际接口契约和相关测试。

- 已确认的运行行为。


### 13.2 必须区分事实与推导

例如：

```
已确认：
目标项目存在某个 Interceptor，实际负责 JWT 鉴权。

推导：
当前 Go Component 的通用身份认证职责可以由该 Interceptor 承担。

仍需确认：
Go 中某项特殊授权判断是否已经由该 Interceptor 或其他组件实现。
```

不能把推导直接描述成已确认事实。

### 13.3 禁止仅凭名称推断

以下判断均不足以单独支持结论：

- 目录叫 `service`，所以所有业务逻辑都应该放进去。

- 类叫 `Client`，所以它已经覆盖 Go 中所有下游调用行为。

- 项目使用 Spring Security，所以 Go 中的全部鉴权逻辑都已实现。

- 项目使用 MyBatis，所以 Go 中的所有持久化行为都已保留。

- 项目使用 Spring DI，所以 Go 中的所有上下文管理代码都可以删除。

- 项目有统一异常处理，所以 Go 中所有错误路径都可以合并。

- 项目存在 Metrics 包，所以 Go 中所有指标语义都已经得到保留。


必须结合具体实现和实际职责判断。

---

## 十四、明确禁止的推导方式

### 14.1 禁止从 Go 文件数量推导 Java 文件数量

错误方式：

```
Go 有 8 个文件
    ↓
创建 8 个 Java 文件
    ↓
删除几个框架文件
    ↓
得到 Java 文件树
```

正确方式：

```
研究目标 Spring Boot 项目
    ↓
识别 Go 的实际职责与必要行为
    ↓
确定每项职责的 Java 承载位置
    ↓
识别现有组件复用与框架职责吸收
    ↓
根据目标项目的组件边界决定拆分和合并
    ↓
生成理论 Java 文件树
```

### 14.2 禁止用固定三层架构代替实际分析

不能机械地把所有内容安排为：

```
Controller
    ↓
Service
    ↓
Repository
```

目标项目已有 `api` 与 `rpc` 两个不同的组织区域，并且各自有明确的包职责。

必须根据实际调用链和目标项目既有架构判断职责归属，而不是用通用三层架构覆盖现有设计。

### 14.3 禁止把 Spring Boot 当作自动实现业务逻辑的工具

Spring Boot 能提供框架机制，但不会自动实现当前业务所需的：

- 特殊业务判断。

- 状态转换规则。

- 数据查询条件。

- 业务授权条件。

- 事务边界与部分成功语义。

- 下游调用的特定顺序。

- 错误转换和业务副作用。

- 指标触发条件。

- 其他实际业务规则。


只要这些职责仍然影响业务行为，就必须在理论文件树中找到合适的承载位置，或者明确指出由哪个已有组件实际承担。

### 14.4 禁止为了完整性而创建空组件

不得为了使文件树看起来完整而创建：

- 没有实际职责的 Service。

- 只用于对应 Go 文件名称的 Java 类。

- 没有实际配置需求的 Config 类。

- 没有实际业务异常需求的 Exception 类。

- 没有实际指标需求的 Metrics 类。

- 没有实际启动任务的 Bootstrap 类。

- 没有必要的中间层或纯转发组件。


但是，不能以避免空组件为理由，省略仍然需要实现的职责。

### 14.5 禁止未经依据就改变目标项目架构

本任务允许根据 Java 的实际职责组织代码，但不是重新设计整个目标项目。

不得无依据地：

- 创建新的顶层模块。

- 将 API 与 RPC 的职责混在一起。

- 引入目标项目没有采用的通用架构模式。

- 重新划分所有包的职责。

- 设计一套与目标项目现有组织方式不一致的目录体系。


如果现有包结构确实无法合理承载某项必要职责，必须先说明具体原因，再提出最小范围、具有明确依据的调整建议。

---

## 十五、最终判定标准

理论 Java 文件树只有同时满足以下条件，才算推导完成。

### 15.1 业务职责完整

Go Component 中所有需要保留的行为和职责都有明确的 Java 承载位置，或有真实存在的机制承担。

不能因为 Java 文件减少，就认为某项职责可以消失。

### 15.2 符合目标项目的组织方式

Java 文件树优先采用目标 Spring Boot 项目已有的包结构、组件边界和组织惯例。

不能仅为了与 Go 文件对应而保留不必要的 Java 文件边界。

### 15.3 框架吸收有真实依据

每一项被标记为 `ABSORB` 的职责，都必须能够指出实际承担它的 Spring / Java 机制。

如果只是由已有业务组件承担，应标记为 `REUSE`，不能笼统地说成框架吸收。

### 15.4 合并与拆分有明确理由

文件合并不是为了让 Java 文件更少，文件拆分也不是为了让 Java 文件数量更接近 Go。

两者都必须符合目标 Java 项目的职责组织方式。

### 15.5 不把推导结果伪装成既有事实

对没有明确证据的包归属、组件复用或文件边界，应明确标记为推导建议或待确认事项。

### 15.6 最终交付物是理论文件树

最终必须给出实际的 Java 包路径、文件名、文件职责、来源职责和必要的组织理由。

不能只给出抽象架构图、概念列表或“建议按三层架构组织”的泛化说明。

也不能只给出 Go 文件与 Java 文件的逐项对应表，而没有真正推导出 Java 文件树。

## 十六、最终执行原则

整个任务始终遵循以下原则：

> **Go 源码决定迁移什么，目标 Spring Boot 项目决定如何组织，Spring / Java 实际提供的机制决定哪些实现职责可以被直接吸收。**

> **保留业务职责，不等于保留 Go 的文件划分。**

> **使用 Spring Boot，不等于机械地套用三层架构。**

> **允许多个 Go 文件合并到一个 Java 组件，也允许一个 Go 文件拆分到多个 Java 组件。**

> **框架职责吸收、现有组件复用、业务职责合并和职责拆分是不同的事情，不得混为一谈。**

> **不要求 Java 文件数量接近 Go，但每一项需要保留的职责都必须有明确的承载位置。**

> **最终结果必须是一棵真正按照目标 Spring Boot 项目组织方式推导出来的理论 Java 文件树，而不是一棵改了文件扩展名、删除少数 Go 基础设施文件后得到的 Go 文件树。**
