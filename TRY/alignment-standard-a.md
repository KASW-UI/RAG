# A 档对齐标准：行为层对齐（判定边界表）

> **建立时间**：2026-10-27 · Jason 拍板（选项 A）
> **状态**：🔴 **草稿，放在 `TRY/` 下，尚未签字** —— 升为正式政策需走 AGENTS.md §5.1/§5.2（issue → spec → PR）
> **地位**：**前置的判定边界**，用来省掉「每发现一条新差异就重新争论算不算 bug」的成本
> ⚠️ **它不替代逐条证据**：逐条证据仍以各域台账 + `docs/Intentional_Deviations/` 为准；本文件只定**判据**

## 0. 一句话

**对外能看见的：一个字都不能差。对内怎么写的：随便，但必须留痕。**

这条标准不是教条，是**已经付过代价换来的**：2026-10-18~10-20 曾短暂拿 Java 版当基准，10-20 回头逐行审计的结果是
**Go 0 缺陷 vs RAG 11 处回归，且 11 处全部集中在「把 Java 写法换成更地道的 Spring 写法」的位置**
（`docs/DRIFT/_cross/truth-source-switches.md`）。

那 11 处：`CreateAdmin` 事务 self-invocation 失效 · 邀请码缺 `FOR UPDATE` · `extra_info` jsonb 写入丢 typeHandler ·
`SelectAvatar` 响应 `is_current` 陈旧 · `UpdateSelf` 空 email 清空列 · uid 解析静默转 0 · `success` 字段语义反转 ·
`JwtUtil` 密钥补齐被删 · HTTP 状态码语义变更 · Flyway 双服务版本冲突 · `@ResponseBodyAdvice` 二次包裹。

⚠️ **共同点（必须记住）**：**没有一个是编译错误，没有一个是测试红** —— 全是「绿的、看着没毛病的、跑起来跟 Go 不一样」。
⇒ **自由发挥在这个项目里的准确含义 = 主动去制造那 11 处同类问题。**

## 1. 判定边界表（四个档）

> **用法**：发现一条差异 ⇒ 走 §2 的 5 步流程 ⇒ 落到下面某一档 ⇒ 按该档的**判定标准**处理，不再重新争论。

### 档 1 · 必须逐字对齐（对外可观察面）

> 判据：**客户端或运维能看见的东西**。改了就有人能发现行为不同。

| # | 维度 | 判定标准 | 怎么验 | 证据强度下限 |
|---|---|---|---|---|
| 1 | HTTP 路径与方法 | 路径串、方法名**逐字节相同** | 真 Tomcat 发请求 + 逐字节比对响应 | 双侧活体 |
| 2 | 错误码 / 业务码 | **码值 + 文案 + 载体**（gRPC code / HTTP 状态）三者全等 | `tools/errmsg-probe/` 逐字节对拍 | 双侧活体 |
| 3 | 响应体结构 | 字段名 + 类型 + **presence**（该字段到底在不在） | 真容器响应体逐字节 | 双侧活体 |
| 4 | HTTP 状态码 + reason phrase | 数值 **+ 短语**（短语也算，见 `DRIFT-MSGAPI-011`） | 真 Tomcat（**MockMvc 测不到**） | 双侧活体 |
| 5 | 响应头 | `Content-Type` / `nosniff` / `Traceparent` 等 | 真 Tomcat 抓头 | 双侧活体 |
| 6 | JWT claim | **名称 + 必需性（presence）+ 值语义** | 双侧签发后解 claim | 双侧活体 |
| 7 | proto 契约 | message 名 / 字段名 / **字段号** / 类型 / 枚举值 | 静态逐条 + **消费方式已验** | 静态源码（+消费方式） |
| 8 | 解析失败行为 | 非法输入 → 什么码、什么文案、**是否静默兜底** | 双侧喂同一批非法输入 | 双侧活体 |
| 9 | 数据库表结构 | 列名 / 类型 / 长度 / 可空 / DEFAULT / 索引 / 唯一约束 | 双侧活体建库后逐列对照 | 双侧活体（真 PG） |
| 10 | 事务边界 | 哪些写操作在**同一个**事务里 | 源码 + 运行时行为 | 真 PG |
| 11 | 行级锁 | 哪些读-改-写路径加了**行锁** | 源码 + 并发实测 | 真 PG（并发） |
| 12 | 超时 / deadline | 默认值 + 绑到谁 + 往哪传 | 源码 + 双侧探针 | 双侧活体 |
| 13 | 保护链阈值 | 熔断 / 降载 / 连接数 / 请求体上限 | 源码 + 越限实测 | 双侧活体 |
| 14 | 归一化与兜底 | uid / keyword 等的解析、截断、静默兜底 | 双侧喂同一批输入 | 双侧活体 |

⚠️ **第 3 条的 presence 语义**：`optional` 字段「有没有这个 key」本身就是行为差异（不是"值为空"）。
⚠️ **第 8 条 / 第 14 条**：**静默兜底是最贵的漂移**（Go 报错 vs RAG 转 0 ⇒ 调用方拿到不同的数据，测试常常照样绿）。

### 档 2 · 行为等价即可（对外不可观察）

> 判据：**客户端和运维都看不见的东西**。怎么写都行，但**必须留痕**。

| 维度 | 允许的自由 | 但必须满足 |
|---|---|---|
| 包划分 / 类结构 | 任意 | — |
| ORM API 选型 | GORM ↔ MyBatis-Plus 随意换 | 最终表结构落在档 1 |
| 注解风格 / 注入方式 | 任意 | — |
| 异常包装方式 | 任意 | **最终 wire 契约落在档 1** |
| DDL 脚本组织与启动机制 | 幂等重放 ↔ Flyway 随意换 | **最终表结构落在档 1** |
| 日志 / 埋点写法 | 任意 | **span 属性值落在档 1**（A9 轴） |
| 事务注解写法 | 任意 | **事务边界落在档 1** |
| Boot 装配方式 | 任意 | — |

**留痕要求（三段式 javadoc，AGENTS.md §3.2）**：

```java
/** <p>L4 idiomatization：<改成了什么写法>。
 * <p>Go 出处：<真源文件:行号>。
 * <p>语义等价论证：<逐条论证，且指出本段比 Go 多做了什么>。 */
```

⚠️ **回答不了「这段比 Go 多做了什么？语义还一样吗？」= 无出处的 idiomatization = 不可 review，不得合入。**
⚠️ 历史上 **11 处回归全部属于「无出处的 idiomatization」** —— 注释写得很完整，唯独没一处标注 Go 出处，
导致 review 时无从判断「这是必要表达差异，还是悄悄改了行为」。

## 2. 处理一条新发现的差异：5 步（不许跳步）

```
① 查白名单 ── 是档 4？ ──→ 收工（已签字 = 决策，别动）
      │否
      ↓
② 定性质 ──→ 落档 1 / 档 2 / 档 3 / 档 4
      ↓
③ 定方向 ── Go 那边是「改写了的」还是「原样抛的」？  ← 决定是 RAG 错还是 RAG 更准
      ↓
④ 登记 ── 证据强度 + 核对日期 + Go 出处（文件:行号）
      ↓
⑤ 要改的话 → 先改/删错误断言，再改实现
```

⚠️ **第 ③ 步是最容易出错的一步**，也是历史上代价最大的一步：

- **第三十六轮 E47 全面订正**：先前只看了 RAG 侧的 catch 形态（24 处宽 catch + 3 处静默降级），**没核 Go 侧**
  ⇒ **定性方向完全相反** ⇒ **21 处销案**（`comment`/`like`/`follow`/`article` 四域的 Go 侧同样改写）
  ⇒ 真正的漂移另有其人（`user-rpc`/`admin-rpc` = RAG 更准 ⇒ 走有意偏离候选；`message` = RAG 更糊）。
- **PIT-GLOBAL-051 原文警告**：**「只读盘点的结论登记前必须抽核到 Go 行号」**。
  ⇒ **杀伤力不在台账，而在域 owner 照着台账去改代码 ⇒ 把本来正确的 catch 改坏 ⇒ 制造新漂移。**

⚠️ **第 ⑤ 步有专门条款**（AGENTS.md §3.3.2）：**修漂移时先改/删错误断言，再改实现** ——
否则会先撞上「测试红了」而误以为自己改错了方向。

## 3. 证据强度四档（决定 ✅ 怎么读）

| 档 | 名称 | 含义 | 拿到了吗 |
|---|---|---|---|
| 1 | 静态源码对照 | 只读代码 | 4 个 api（`article-api`/`admin-api`/`message-api`/`user-api`）的上限 |
| 2 | 真启动 | 进程真的起来了 | — |
| 3 | 真依赖（真 PG / 真 Kafka / 真 Redis） | 真的连着外部依赖跑 | 7 个 rpc 的上限 |
| 4 | **双侧活体对拍** | **Go 侧和 RAG 侧同时活着跑同一个请求** | 只有 `like-api` / `hot-api` / `follow-api` / `follow-rpc` 等少数 |

> **⚠️ 台账里的 ✅ 一律读作「在该证据强度下一致」，不是已闭环。**
> ⇒ 任何一条 ✅ 都必须带**证据强度 + 核对日期**，否则按 `UNKNOWN` 处理（AGENTS.md §6 状态表纪律）。
> ⇒ **升级证据强度本身就会产出新条目** —— 这是设计使然，不是失控。

### 3.1 「升级」前必须先证明上一档**真的做到过**

⚠️ **E62 是模板**：第四十一轮才发现探针的**施加侧和观测侧连的是两个不同的容器** ⇒ 锁从未生效
⇒ **前三轮「真跑」拿到的全是无效观测**（不假绿，但**结论是误诊**）。

⇒ **纪律**：把一档升到更高档之前，先确认**低档的结论本身是有效的**。
**「跑绿」不是「对」**；**「跑过了」也不是「跑成了」**。

### 3.2 两条否定性结论的硬纪律

| 纪律 | 出处 | 要点 |
|---|---|---|
| 否定性结论进台账前**必须两次独立检索都为空**，且**空结果的 grep 模式要写进台账** | PIT-GLOBAL-059 | 第四十六轮真犯过：第一次扫 `zrpc.MustNewClient\|\.Call(ctx\|RpcClient` ⇒ **0 命中** ⇒ 写下「Go 没有出向 rpc 调用」；换前缀再扫 ⇒ **5 处命中** ⇒ **结论整个反转** |
| 守门脚本的**覆盖范围本身**就是缺陷面 ⇒ 枚举必须显式注释「**不覆盖哪些**」 | PIT-GLOBAL-030 | L11 手工查 10 个 rpc，**漏了 `hot-rpc`** ⇒ 手工必漏 |

## 5. 这份文件的效力边界（三条，越界即失效）

1. **它定判据，不定结论。** 任何一条 ✅/🔴 的**具体证据**仍在各域台账 + `docs/Intentional_Deviations/`。
   ⇒ **不许拿本文件当「已对齐」的凭据**。
2. **它不改变 AGENTS.md 的政策。** 真源仍是 Go，Go 仍是唯一判定标准；本文件只是**把「什么算问题」前置固化**。
3. **它是草稿。** 放在 `TRY/` 下、**未签字** ⇒ 现在可以随便改；**一旦签字并升为正式政策**，
   改它就得走 PR 流程，且**已按旧标准登记的条目要按新标准复核一遍**。
