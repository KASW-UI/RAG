## A.5 资源清理与超时预算

⚠️ **本链路踩过的最深的一个坑（值得单独讲）** —— **超时预算的作用域**：
- Go 的计时器在 **Authorize 之后**起算 ⇒ **验签耗时不计入** 3s 预算；
- RAG 的计时器在 **Filter 外层** ⇒ **验签耗时计入**。
⇒ ⇒ 同一个「验签很慢」的故障，Go 侧返回 `200 + 1015`，RAG 侧返回 `503 "Request Timeout"` ⇒ **可观察差异**。
⇒ 已作为 `DRIFT-FOLLOW-010` / `DRIFT-USERAPI-009②` **域内推广并修复**（本轮 R2 的域内闭环项之一）。

# 链路 B · 文章发布 → 同步出箱 → 事实投递 → 不可变信封

## B.1 触发条件与入口

`article-api` 的发布类端点（7 个 handler 之一）⇒ gRPC ⇒ `article-rpc`。

| | Go | RAG |
|---|---|---|
| 入口 | `service/article/api/internal/handler/routes.go` | `service/article/article-api/controller/ArticleController.java` |
| 服务端 | `service/article/rpc/internal/logic/`（6 rpc） | `service/article/article-rpc/impl/ArticleServiceGrpcImpl.java` |
| 启动建库 | `model.InitDB` ⇒ `AutoMigrate`（`article` + `article_sync_outbox`） | Flyway `V8`（`article`）· `V9`（`article_sync_outbox`）· `V10`（社区修订） |
| 额外 SQL | `002_community_revision.sql`（Go 侧手写） | 同语义在 `V10` 里 |

## B.2 关键调用与职责

| 环节 | 职责 | 关键设计 |
|---|---|---|
| 领域写 | 写 `article` | — |
| **同事务写 outbox** | 写 `article_sync_outbox` | ⚠️ **业务写与 outbox 写必须同事务** ⇒ 否则「业务成功但事件丢了」⇒ 投递端永远看不到 |
| 投递 | 取件 → 投递 → 标记状态 | **部分索引取件**（按状态过滤）⇒ 取件不扫全表 |
| 事实落地 | 写 `article_revision` / `article_publication` / `article_domain_outbox` | **修订号推进**（下游靠它判断「我是不是最新」） |
| **不可变信封** | 已投递的事实**不可改写** | 🔴 **由数据库触发器强制**，不是应用层自觉 |

## B.3 数据变化

```
article-api 发布
   └─▶ article-rpc（同一事务）
          ├─ INSERT article
          └─ INSERT article_sync_outbox        ← 同事务！
                 └─▶ 投递器取件（按 status 的部分索引）
                        └─▶ INSERT article_revision / article_publication / article_domain_outbox
                               └─▶ 触发器：BEFORE UPDATE FOR EACH ROW
                                     └─ 试图改写已投递事实 ⇒ RAISE EXCEPTION
```

## B.4 成功 / 失败路径

| 路径 | 行为 | 证据 |
|---|---|---|
| 正常发布 | 业务表 + outbox 同事务落库 | ✅ 双侧活体 |
| 投递失败 | outbox 状态未推进 ⇒ **可重投**（不丢） | ✅ 幂等消费设计 |
| **试图改写已投递事实** | 🔴 **触发器抛异常 ⇒ 拒绝** | ✅ **触发器形式 + 函数体属性**双侧对比 |
| 修订号冲突 | 由 `article_revision` 的唯一性挡住 | ✅ 索引/约束层已核 |

## B.5 设计理由与适用边界

- **为什么用 outbox 而不是「业务成功后直接发消息」**：直接发 ⇒ 业务成功但发消息失败 ⇒ 事件永久丢失（且无痕迹）。outbox 把「事件」变成**同事务内的数据行** ⇒ 「要么都成，要么都不成」⇒ 投递可重试、可对账。
- **为什么不可变要落在数据库**：应用层自觉 = 「只要有人忘了就破」。触发器是**最后一道** ⇒ 任何写入路径（应用 / 运维 / 脚本）都绕不过。
- **适用边界**：本机制**只覆盖「事实信封」**（已投递的出向事件），**不覆盖**业务表本身的可变性（业务表本来就该可变）。

## B.6 测试证据与验证结果

| 证据 | 内容 | 强度 |
|---|---|---|
| DDL 逐列对比 | article 域 **5 张表** · 类型/长度 0 差异 | **L3**（真 PG 16） |
| 触发器对比 | 数量、形式（timing / 事件集 / 粒度 / constraint / WHEN）、函数体属性（函数名 / 返回类型 / 参数 / volatility / 语言）**逐条一致** | **L3** |
| **源码 ↔ 活库** | 仓里的 `V8`/`V9`/`V10` 在干净临时库重放 ⇒ 与活库**逐项一致** | **L3 + 变异必红** |
| `ArticleTransactionWiringTest` | 事务边界**真 PG** 验证 | **L3** |

**不足**：🔴 **触发器函数体的「语义」机器判不了**（它到底在拒绝什么）⇒ **人工逐条核对**（台账 `docs/DRIFT/global/lanes/L10-ddldeep.md` §8.2）⇒ **机器只保证「形式一致」，不保证「语义一致」**。

# 链路 C · 点赞 → 计数聚合 → 出箱 → 事实流 → 跨域投递

## C.1 触发条件与入口

`like-api` 的点赞端点（6 个 handler 之一）⇒ `like-rpc`。

## C.2 关键调用与职责（**本项目技术特点最集中的一条**）

| 环节 | 表 | 职责 |
|---|---|---|
| 记录点赞 | `like_record` | 业务事实 |
| **幂等消费** | `like_consume_inbox` | ⚠️ **同一 `event_id` 重复投递 ⇒ 只生效一次** ⇒ 消息系统「至少一次」语义下的正确性基础 |
| 出箱 | `like_outbox_event` | 同事务写入 |
| 事实流 | `like_fact_stream` | 已投递的事实（**单调版本号**） |
| 跨域 | `like_domain_fact_outbox` | 交给下游域（comment / favorite 等）消费 |

## C.3 数据变化

```
like-api 点赞
  └─▶ like-rpc
       ├─（同事务）INSERT like_record + INSERT like_outbox_event
       └─▶ 投递器
            ├─▶ INSERT like_consume_inbox（幂等键 event_id ⇒ 重复即跳过）
            └─▶ INSERT like_fact_stream（版本号单调）
                  └─▶ INSERT like_domain_fact_outbox ⇒ 下游域按修订号消费
```

## C.4 成功 / 失败路径（含本轮修掉的一个真缺陷）

| 路径 | 行为 | 状态 |
|---|---|---|
| 正常点赞 | 计数 +1，事实落库 | ✅ |
| **同一事件重复投递** | `like_consume_inbox` 命中 ⇒ **不重复计数** | ✅ 幂等 |
| **双失败（两个下游同时失败）** | ⚠️ **原实现少传 `error`** ⇒ 客户端拿不到真实原因 | ✅ **已修 + 已销案**（global `E60`）<br>修法 = `LikeTaskProgressPublisher.publish` **三段式分流** ⇒ 真日志 `error_code=5011` ⇒ 已修 + 已守门 + 实跑 **4/4 绿** |
| 事实投递链路整体 | ⚠️ 原记「6 个 4 行骨架」⇒ **已实测过时** | **三段拆分**：A 投递链路 ✅ 闭环 · B 权威读语义 ✅ 闭环 · **C 暴露形态待拍板** ⇒ 用户 2026-10-29 裁定 = **登记为 C 类（阶段二暂缓）** |

## C.5 设计理由与适用边界

- **为什么要有 `like_consume_inbox`**：Kafka 的投递语义是「**至少一次**」⇒ 消费者**必然会收到重复消息** ⇒ 幂等键必须**落库**（不能只在内存里判）。
- **为什么事实流要单调版本号**：下游要判断「我手上的版本是不是最新」⇒ 需要一个**可比较的单调量** ⇒ 而「时间戳」不是（时钟会回拨、会并发）。
- **适用边界**：**只保证「不重复处理」**；**不保证「不丢」**（丢 ⇒ 需要对账/补偿，阶段二）。

## C.6 测试证据与验证结果

| 证据 | 内容 | 强度 |
|---|---|---|
| DDL 逐列 | like 域 **5 张表** · 类型/长度 0 差异 · **可空性 0 / DEFAULT 0** | **L3** |
| 额外资产 | **仅 RAG 有**：索引 2 + `CHECK` 2 + 不可变触发器 1 ⇒ **RAG 更严**（非漂移） | **L3** |
| 源码 ↔ 活库 | `V1`~`V6` 重放 ⇒ 与活库逐项一致 | **L3 + 变异必红** |
| 错误码契约 | `LikeErrorContractTest`：**29 个码逐条 1:1** + 文案表 + 未知码回落 + `CodeError` 序列化（期望值抄自 Go `errmsg.go:37-67`/`:69-99`/`:101-107`） | **L3** |
| `E60` 销案 | 三段式分流 ⇒ 真日志 `error_code=5011` ⇒ 已修 + 已守门 + 实跑 4/4 绿 | **L4** |

**不足**：① `like` 域的**事实投递链路**暴露形态待拍板（C 类暂缓）② `like` 域 8 条 Unresolved（U-01~U-08）**台账未标关闭** ⇒ 销号中（§九 G-14）。

# 三个机制的「阶段 1 竞争力」小结（P1 口径）

`docs/twoStage.md` §2.1 P1 要求：至少选 **2~3 个**机制，形成「源码分析 → 测试设计 → 实际验证 → 结果解释」的完整闭环。本项目取 **M1 / M2 / M3** 三个：

| P1 要求的 9 项 | M1（JWT + fail-open） | M2（outbox + 触发器不可变） | M3（幂等消费 + 事实流） |
|---|---|---|---|
| 1. 解决什么具体问题 | 身份伪造 / 会话撤销 | 事件丢失 / 事实被改写 | 重复处理 / 版本乱序 |
| 2. 为什么需要该机制 | 分布式服务需可验证身份 | 「应用层自觉」不足以保证不可变 | Kafka 至少一次 ⇒ 必须幂等 |
| 3. 真实调用链如何运行 | A.2 | B.2 | C.2 |
| 4. 关键状态/数据/资源如何变化 | A.3 | B.3 | C.3 |
| 5. 正常情况下如何工作 | A.4 | B.4 | B.4 | 
| 6. 失败时如何表现 | A.4（7 类码） | B.4（触发器拒绝） | C.4（幂等跳过 / 三段式分流） |
| 7. 如何通过测试证明有效 | 9 种 JWT 边界双侧活体 | 触发器形式 + 函数属性对比 | 29 码逐条 + 4/4 实跑 |
| 8. 当前实现的适用边界 | 保护面未自动比对 | **函数体语义机器判不了** | 只保证不重复，**不保证不丢** |
| 9. 进一步提高可靠性需要改进什么 | 保护面自动比对 | 函数体语义人工核对自动化 | 对账 / 补偿（阶段二） |

⇒ **P1 闭环成立**：三个机制**都有源码分析 + 测试设计 + 实际验证 + 明确的适用边界与不足**。
⇒ ⚠️ **不得**把它读成「生产级可靠性已达标」—— 三个机制的**边界行（8/9）**都明确写着还差什么。
